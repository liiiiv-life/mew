이 문서는 mew에서 파일을 열 때의 체감 지연을 줄이기 위한 현재 진단과 실행 순서를 정리한 reference다. 아직 채택되지 않은 저장소·캐시 구조는 결정으로 간주하지 않는다. 구현하면서 영구 저장 방식이나 협업 수명 모델을 바꾸게 되면 별도 ADR로 확정한다.

## 구간을 나눠 본다

"파일 열기"를 하나의 시간으로 뭉치지 않는다.

| 구간 | 시작 | 완료 |
| --- | --- | --- |
| 콜드 오픈 | 아직 열지 않은 파일 클릭 | 본문을 처음 조작할 수 있는 프레임 |
| 캐시 오픈 | 본문 캐시가 있는 파일 클릭 | 캐시 본문을 조작할 수 있는 프레임 |
| 열린 탭 전환 | 이미 열린 탭 선택 | 해당 탭을 조작할 수 있는 프레임 |
| 세션 복원 | 새로고침·재시작 | 각 칸의 활성 탭을 조작할 수 있는 프레임 |
| 협업 준비 | 활성 파일 선택 | 원격 변경 송수신이 가능한 시점 |

본문을 먼저 볼 수 있는 시간과 협업 동기화 완료 시간도 분리한다. 협업 준비가 늦더라도 캐시된 본문과 편집기 껍데기를 먼저 보여 줄 수 있는지 별도로 판단한다.

## 현재 경로와 병목 후보

2026-08-25 코드 기준이다. 아래는 정적 코드 조사로 확인한 경로이며, 병목의 실제 비중은 성능 계측으로 확정해야 한다.

### 탭 상태와 복원

- `src/hooks/useTabs.ts`의 `openFileIn`은 본문 캐시를 동기로 읽고 탭 상태를 먼저 만든 뒤 `/api/file`과 `/api/rules`를 병렬 요청한다.
- 2026-08-26부터 본문·규칙·저장 상태 갱신은 같은 경로를 연 칸만 바꾼다. 나머지 칸과 탭의 객체 identity를 보존하므로, 한 파일 응답이 앱 전체의 재렌더를 유발하지 않는다. 같은 경로를 여러 칸에서 연 경우에는 그 칸들만 함께 갱신한다.
- 세션 복원은 탭 껍데기·순서·배치와 캐시 본문을 전부 즉시 복원한다. 2026-08-26부터 본문·규칙 요청은 각 칸의 활성 탭에만 즉시 보낸다. 비활성 탭은 `deferredLoad` 상태로 남고 사용자가 선택할 때 기존 전체 본문 경로로 읽는다. 유휴 프리패치 큐는 아직 넣지 않았다.
- 열린 탭 메타데이터는 `states`가 바뀔 때마다 전체 프로젝트·칸·탭을 다시 직렬화해 `localStorage`에 쓴다.

### 본문 캐시

- `src/utils/contentCache.ts`는 메모리 LRU 뒤에 `localStorage`를 둔다. 디스크 계층의 `getItem`·JSON 파싱·직렬화·`setItem`은 모두 메인 스레드 동기 작업이다.
- 최대 512 KiB 본문을 클릭 경로에서 파싱할 수 있고, fetch 완료와 자동 저장 때도 본문과 LRU 순서를 동기로 기록한다.
- 캐시는 수정 시각·버전·ETag를 갖지 않는다. 캐시를 먼저 그려도 매번 전체 본문을 다시 요청한다.

### 편집기와 협업

- `src/components/EditorPane.tsx`는 활성 파일만 편집기로 렌더한다. 파일 전환 시 plain은 CodeMirror 문서를 교체하거나 구성을 다시 만들고, Hotview는 Markdown을 ProseMirror 문서로 다시 반영한다.
- 편집 가능한 주 화면은 활성 파일별로 `useCollab`의 `Y.Doc`·awareness·WebSocket을 새로 만든다. Hotview의 `useEditor`는 `collab.ydoc`이 바뀌면 파일별 Y.XmlFragment 바인딩 때문에 확장 전체를 포함한 에디터를 다시 만든다.
- 파일을 바꾸면 댓글도 별도로 읽는다. 본문 바이트 수는 `TextEncoder`로 본문 전체를 다시 순회해 계산한다.
- 스크롤 복원은 저장 위치를 지키기 위해 최대 600 프레임 동안 편집기 DOM과 높이를 검사할 수 있다. 기능 자체는 [ADR 0038](../../../.mew/docs/decisions/0038-mew-scroll-restore-on-reload.md)·[ADR 0039](../../../.mew/docs/decisions/0039-mew-scroll-restore-on-tab-switch.md)의 현재 결정이다.

### 서버 요청

- `/api/file`은 본문을 동기 `readFileSync`로 읽는다. 로컬의 작은 파일은 보통 짧지만 큰 파일·느린 파일시스템에서는 Node 이벤트 루프를 막을 수 있다.
- `/api/rules`는 MOC 커버리지와 파일 링크를 동기 검사한다. 전체 커버리지는 3초 TTL로 재사용하지만 만료 뒤 첫 요청은 docs 트리를 훑고, 개별 파일 링크 검사는 매번 수행한다.
- 파일 본문·규칙·댓글이 서로 다른 응답과 상태 갱신으로 들어온다. 이 중 규칙과 댓글은 첫 본문 표시의 선행조건이 아니다.

## 큰 파일의 포커스 주변 우선 표시 (후속 설계)

2026-08-26부터 검색 결과처럼 목표 줄이 확정된 512 KiB 이상 plain 파일은 `/api/file`의 anchor 요청으로 목표 주변 400줄을 먼저 받는다. 서버는 그 범위가 끝날 때까지 async stream으로만 읽고, 클라이언트는 실제 전역 줄번호를 붙인 읽기 전용 CodeMirror preview를 즉시 보인다. 전체 본문 요청은 preview 뒤에 시작하며 완료될 때만 cache·편집·협업·댓글의 기존 경로로 전환한다. 계약의 근거와 경계는 [ADR 0082](../../../.mew/docs/decisions/0082-mew-large-file-anchor-preview.md)다.

아직 `0, +1, -1 …` 조각 보충과 전체 scrollbar placeholder는 구현하지 않았다. 첫 preview를 빨리 보인 뒤 전체 문서로 안전하게 전환하는 1단계만 적용했다. CodeMirror는 **전체 문서가 준비된 뒤** DOM을 화면 viewport 중심으로 제한하지만, 네트워크 전송·문서 생성·구문 처리의 선행 비용까지 줄이지는 않는다. Markdown Hotview는 원문 전체를 ProseMirror 문서로 파싱해야 하므로 같은 효과를 기대하기 더 어렵다.

목표는 예를 들어 `abc.md:1536`을 열 때, 1536줄을 화면 위쪽 약 10% 지점에 먼저 보이게 하고 가까운 조각을 `0, +1, -1, +2, -2 …` 순서로 비동기 보충하는 것이다. 이 절은 이를 위한 **후속 후보 설계**이며, 아직 API·협업 계약을 채택한 결정은 아니다.

### 적용 범위와 진입 조건

- 먼저 마지막 스크롤 위치·검색 결과·`경로:줄` 링크처럼 목표 줄이 이미 있는 경우에만 쓴다. 목표가 없거나 작은 파일이면 기존 전체 본문 경로가 더 단순하고 빠르다.
- 첫 도입 대상은 충분히 큰 **비협업 plain 텍스트**만이다. Markdown Hotview, 편집 중인 협업 문서, 외부 파일은 전체 본문 경로를 유지한다.
- 임계 크기·줄 수는 계측으로 정한다. 작은 문서까지 쪼개면 요청·상태·placeholder 비용이 이득보다 커진다.
- 포커스 조각을 즉시 읽을 수 있어도 파일이 바뀐 경우의 일관성은 유지해야 한다. 모든 조각 응답은 같은 파일 버전(최소 mtime·size, 가능하면 ETag)에 묶고, 버전이 달라지면 부분 상태를 버리고 최신 전체 또는 최신 조각 세션을 다시 시작한다.

### 전송과 보충 순서

1. 클라이언트는 `path`, `anchorLine`, `chunkLines`를 주고, 서버는 `totalLines`·버전·반환 줄 범위와 함께 anchor를 포함한 첫 조각을 돌려준다. 첫 조각은 anchor의 위쪽 여백을 약 10%로 둔다.
2. 화면은 문서 앞·뒤의 아직 없는 부분을 추정 높이 placeholder로 두고 첫 조각을 곧바로 표시한다. scrollbar 비율은 전체 줄 수와 관측한 평균 줄 높이로 근사하며, 실제 줄 높이가 확인될 때만 보정한다.
3. 취소 가능한 단일 큐가 인접 조각을 `0, +1, -1, +2, -2 …` 순서로 요청한다. 사용자가 반대 방향으로 스크롤하면 그 방향을 우선하고, 탭·프로젝트 전환 또는 파일 버전 변경 시 남은 요청을 취소한다.
4. 충분한 조각이 이어져 전체 파일이 완성되면 일반 CodeMirror 상태로 한 번 전환한다. 이 전환은 스크롤·선택을 보존하고, 준비 뒤에만 편집·댓글·lint·협업을 활성화한다.

서버가 매 조각마다 파일 처음부터 anchor까지 문자열을 훑으면 큰 파일에서 이득이 없다. 따라서 실제 도입 전에는 안전한 UTF-8 경계와 CRLF를 보존하는 줄 오프셋 인덱스(파일 버전에 묶인 메모리 캐시) 또는 동등한 range 읽기 방식을 검증한다. 이 인덱스의 영속화·공유 범위는 별도 결정 없이는 추가하지 않는다.

### 편집·협업·정확성 경계

- 부분 문서는 완전한 문서 모델이 아니다. 첫 버전에서는 읽기 전용 preview이며, 사용자가 입력·댓글·찾아바꾸기·공유 편집을 시작하면 전체 본문 완성 후 기존 경로로 넘긴다. 부분 상태에서 저장해서 아직 받지 않은 본문을 지우는 일은 절대 없어야 한다.
- Yjs/ProseMirror 협업은 전체 문서와 안정된 위치·구조를 전제한다. 부분 문서를 그대로 협업 방에 넣지 않는다. 이를 바꾸려면 [ADR 0035](../../../.mew/docs/decisions/0035-mew-collab-rooms-rust-yrs.md)의 수명·동기화 경계까지 검토하는 새 ADR이 먼저다.
- Markdown은 앞선 frontmatter·목록·코드 펜스가 anchor 부근의 구조를 결정할 수 있다. 완전한 구조를 보장하지 못하므로 Hotview의 부분 파싱은 첫 범위에 넣지 않는다.
- 검색 결과의 줄 번호·선택 위치·스크롤 복원은 전체 파일 줄 번호를 기준으로 유지한다. placeholder는 실제 텍스트가 아니므로 복사·선택·댓글 앵커 대상이 될 수 없다.

### 도입 전 검증과 중단 기준

- 성능 표본에 큰 plain 파일, anchor가 앞·중간·끝인 경우, 빠른 탭 전환·파일 수정·네트워크 취소를 포함한다. 첫 anchor paint와 전체 문서 준비 시간을 기존 전체 읽기와 각각 비교한다.
- 첫 anchor paint가 유의하게 빨라지지 않거나, placeholder 높이 보정이 눈에 띄게 튀거나, 전체 경로보다 메모리·요청 수가 커지면 도입하지 않는다. 그 결과와 재시도 여부는 이 문서 또는 ADR에 남긴다.
- 범위 조회 API·부분 문서 상태·편집 전환을 실제 제품 계약으로 채택하기 전에는 새 ADR을 작성한다. 이는 파일 전송 프로토콜과 협업/저장 불변식을 바꾸는 선택이기 때문이다.

## 개선 우선순위

### 1. 활성 탭 우선 복원

세션 시작 시 탭의 경로·순서·배치는 즉시 복원하되, 본문과 규칙은 각 칸의 활성 탭만 먼저 읽는다. 비활성 탭은 사용자가 선택할 때 읽거나 첫 화면이 안정된 뒤 작은 동시성으로 유휴 프리패치한다.

이 변경은 복원 탭 수에 비례하던 초기 요청·Markdown 파싱·상태 갱신 경쟁을 제거한다. 첫 구현에서는 동시성 1~2의 취소 가능한 큐로 제한하고, 프로젝트를 바꾸면 남은 프리패치를 폐기한다.

**상태 (2026-08-26):** 활성 탭 우선 복원과 선택 시 지연 로드는 구현했다. 비활성 탭의 유휴 프리패치·취소 큐는 계측으로 실제 이득과 경쟁 여부를 확인한 뒤 추가한다. 따라서 초기 본문 요청 수는 열린 전체 탭 수가 아니라 활성 칸 수에 비례한다.

### 2. 첫 표시의 선행조건 축소

클릭 직후 필요한 것은 활성 경로, 본문, 편집기뿐이다. 규칙 배지와 댓글은 첫 조작 가능 프레임 뒤에 읽는다. `/file`과 `/rules`를 합칠지는 계측 후 결정하되, 합치더라도 규칙 계산이 본문 응답을 늦추면 안 된다.

파일 한 건의 본문·editable·규칙 갱신은 영향받는 칸과 탭만 바꾸고, 값이 같으면 상태 객체를 보존한다. `EditorPane`·사이드바·도구 패널도 관련 prop이 변하지 않으면 다시 그리지 않게 경계를 좁힌다.

**상태 (2026-08-26):** `useTabs`의 파일 응답·규칙·저장·되돌리기 갱신을 경로 범위로 한정했다. 한 파일을 열 때 그 경로가 없는 칸은 기존 상태 객체를 그대로 재사용한다.

### 3. 클릭 경로에서 동기 영구 캐시 제거

메모리 LRU는 즉시 표시용으로 유지한다. 새로고침을 넘는 본문 캐시는 IndexedDB 같은 비동기 저장소 후보를 검증하고, 도입한다면 신원·프로젝트 격리를 현재와 동일하게 보존한다. 서버는 수정 시각이나 ETag를 제공해 캐시가 최신일 때 전체 본문을 다시 보내지 않는 방식을 함께 검토한다.

저장소 변경은 계측과 장애 시 폴백 설계 뒤 별도 결정으로 확정한다. IndexedDB 실패나 마이그레이션 실패가 파일 열기·저장을 막아서는 안 된다.

### 4. 편집기 준비 비용 줄이기

- Markdown 파싱, CodeMirror 상태 구성, 댓글 장식 적용을 각각 계측해 가장 큰 구간부터 줄인다.
- 비협업 탭은 최근 문서의 파싱 결과나 편집기 상태를 제한된 LRU로 재사용할 수 있는지 검토한다.
- 협업 탭은 소켓·Y.Doc을 비활성 상태로 계속 살려 두지 않는다. [ADR 0035](../../../.mew/docs/decisions/0035-mew-collab-rooms-rust-yrs.md)가 소켓 풀링을 방 수·유령 커서·수명 정리 문제 때문에 재시도 금지했다. 최근 협업 탭을 통째로 유지하려면 이 ADR을 대체하는 새 결정이 먼저다.
- 본문 바이트 계산은 첫 입력 가능 프레임 뒤로 미루거나 증분 계산한다.

### 5. 큰 파일의 포커스 주변 우선 표시 검증

위 설계는 1~4단계의 계측 결과에서 큰 plain 파일의 전체 본문 전송·생성 비용이 지배적일 때만 검증한다. 일반 파일 열기 전체를 복잡하게 만들지 않고, 적용 대상·읽기 전용 전환·취소·버전 일관성을 작은 실험으로 고정한다.

**상태 (2026-08-26):** 검색 결과의 큰 plain 파일에 anchor preview 1단계를 구현했다. 서버의 첫 range stream은 목표 줄의 앞 약 10%부터 400줄을 반환하고, 이후 전체 본문 응답이 기존 편집기를 연다. 인접 청크 우선순위·placeholder scroll은 이 구간의 실제 first-paint 수치가 충분히 개선됐는지 확인한 뒤 확장한다.

### 6. 스크롤 복원 폴링 교체

스크롤 위치 복원 기능은 유지한다. 편집기 준비 신호, 협업 sync 완료, `ResizeObserver`를 조합해 높이가 변할 때만 재시도하고, 매 프레임 최대 600회 DOM을 조회하는 경로를 없앤다. 탭 전환·분할 리마운트·늦게 뜨는 이미지에서도 위치를 지킨다는 ADR 0038·0039의 결과를 회귀 테스트로 고정한다.

**상태 (2026-08-26):** `EditorPane`의 600 rAF 폴링을 `MutationObserver` + `ResizeObserver`로 교체했다. scroll host·실제 편집 본문이 생기거나 높이가 바뀔 때만 저장 위치를 다시 적용하며, sync가 오지 않는 경우에도 약 10초 뒤 observer를 해제한다.

## 계측과 완료 판정

최적화 전에 브라우저 Performance API와 React Profiler에 최소 다음 지점을 남긴다.

1. 파일 클릭
2. 메모리·영구 캐시 준비
3. `/file` 응답
4. 편집기 생성과 본문 반영
5. 첫 조작 가능 paint
6. 협업 sync 완료
7. 규칙·댓글 완료

**상태 (2026-08-26):** 1~5는 `mew:file-open:<id>:<phase>` Performance mark/measure로 구현했다. DevTools Performance 또는 `performance.getEntriesByType('measure')`에서 `cache-ready`·`file-response`·`editor-ready`·`first-paint`까지의 시간을 비교할 수 있다. `/api/rules`와 `/api/comments`는 첫 paint 뒤에 시작하며 각각 `rules-response`·`comments-response`를 남긴다. 협업 sync 완료 mark는 다음 비차단 작업으로 남아 있다.

콜드 오픈, 캐시 오픈, 열린 탭 전환, 여러 탭 세션 복원을 각각 Markdown·plain과 작은 파일·큰 파일로 나눠 p50·p95를 기록한다. 숫자 목표는 기준선을 얻은 뒤 정한다. 다음 조건 없이 "빨라졌다"고 완료하지 않는다.

- 캐시 오픈과 열린 탭 전환의 첫 표시는 네트워크 응답을 기다리지 않는다.
- 세션 복원의 초기 본문 요청 수는 전체 탭 수가 아니라 활성 칸 수에 비례한다.
- 클릭부터 첫 조작 가능 paint 사이에 본문 `localStorage` 처리로 생긴 Long Task가 없다.
- 규칙·댓글 실패나 지연이 본문 표시를 막지 않는다.
- 협업 문서의 원격 내용, awareness, 자동 저장과 탭별 스크롤 복원이 그대로 동작한다.

## 권장 작업 단위

1. 계측만 추가해 기준선 확보
2. 활성 탭 우선 복원과 선택 시 지연 로드 (구현됨); 계측 뒤 제한된 유휴 프리패치 검토
3. 규칙·댓글 지연과 탭 상태 갱신 범위 축소
4. 비동기 본문 캐시·조건부 서버 조회 검증 및 결정
5. 큰 plain 파일의 포커스 주변 우선 표시 검증(필요 시 ADR 후 구현)
6. 편집기 준비 비용과 스크롤 복원 폴링 최적화

각 단계는 독립적으로 전후 수치를 비교하고 회귀가 있으면 되돌릴 수 있게 나눈다.
