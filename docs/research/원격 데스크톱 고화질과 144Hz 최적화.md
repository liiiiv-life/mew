# 원격 데스크톱 고화질과 144Hz 최적화 조사

현재 GPU 하드웨어 인코딩·WebRTC 직결 구조를 유지하면서 화질과 반응성을 개선할 여지가 크다. FHD/QHD 144fps는 우선 검증할 만한 목표이고, 165fps 이상과 4K는 호스트·수신 GPU와 화면 갱신율에 따라 단계적으로 확장해야 한다. 특히 해상도와 비트레이트를 올리기 전에 **실제 송신 적체를 관측하고 짧게 제한하는 전송 제어**가 필요하다.

분석 기준은 2026-10-07의 작업 트리다. [현재 공통 계약](../development/remote-desktop.md)·[Mac/Linux 계약](../development/remote-desktop-posix.md)을 따른다. 운영 중인 설치본과 작업 트리의 일치는 별도 적용 확인 사항이다. 아래 개선은 제안이며, 실제 144fps 유지율이나 입력에서 화면 변화까지의 개선량을 측정한 결과는 없다. 기존 [최초 연결 측정](../work/remote-desktop-resident-direct.md)은 지속 FPS나 입력 지연 측정과 구분한다.

## 현재 제한과 코드 근거

| 지점 | 확인한 현재 동작 | 확장할 때의 영향 |
| --- | --- | --- |
| Windows 호출 | [gpu-windows.mjs](../../native/remote-desktop/gpu-windows.mjs)의 `start()`가 1920×1080·60fps·초기 6Mbps를 전달 | 높은 원본 해상도도 축소된다. 설정 값을 네이티브까지 전달해야 한다 |
| Windows 네이티브 | [gpu-windows.cpp](../../native/remote-desktop/gpu-windows.cpp)의 `mew_gpu_start()`는 최대 4096×2160·120fps·20Mbps만 허용 | 내부 크기 여유는 있지만 144fps는 호출 값만 바꾸어도 거부된다. 현재 4K 실행 성능을 입증하는 값은 아니다 |
| Mac/Linux | [gpu-posix.mjs](../../native/remote-desktop/gpu-posix.mjs)도 1080p·60fps 고정. [gpu-macos.m](../../native/remote-desktop/gpu-macos.m)·[gpu-linux.cpp](../../native/remote-desktop/gpu-linux.cpp)는 60fps와 최대 6Mbps를 검사 | OS별 네이티브 검증과 실제 캡처·인코더 설정을 함께 변경해야 한다 |
| Mac 프레임 시간 | 캡처 간격 외에도 expected FPS, encode duration, 강제 refresh의 timestamp 보정에 60이 들어간다 | 캡처 간격만 수정하면 시간 정보와 인코더 정책이 서로 달라진다 |
| 가상 화면 | [virtual-display-driver.cpp](../../native/remote-desktop/virtual-display-driver.cpp)의 EDID·target mode가 1920×1080·60Hz | 가상 화면에서 144개의 서로 다른 화면을 얻으려면 모드와 드라이버 검증까지 확장해야 한다 |
| 코덱 협상 | [native-direct.mjs](../../native/remote-desktop/native-direct.mjs)는 H.264 `42e033`과 SDP bitrate 6000kbps 고정 | Constrained Baseline·Level 5.1 광고와 실제 encoder SPS·수신 capability를 함께 맞춰야 한다 |
| 적응 제어 | 같은 파일이 350kbps–6Mbps에서 25% 감속·5% 증속. 손실 3% 또는 jitter buffer 80ms 초과를 사용 | 높은 해상도·고주사율에 필요한 대역폭을 사용할 수 없고, 병목의 원인을 구분하지 못한다 |
| 제어 주기 | [desktop-connection.ts](../../src/utils/desktop-connection.ts)의 연결 후 stats는 약 1초 간격. 호스트 feedback의 최소 간격은 750ms | 짧은 순간의 적체를 발견하기 전에 지연이 누적될 수 있다 |
| worker 전달 | [native-host.mjs](../../native/remote-desktop/native-host.mjs)는 `direct.frame()` 호출 직후 worker에 ACK | 압축 프레임 하나라는 IPC 제한은 브라우저 수신·표시나 하위 전송 큐의 비움을 확인하는 제한이 아니다 |
| 송신 큐 검사 | `Track.bufferedAmount()`가 없으면 0을 반환 | 현재 설치 바인딩에서 192/256KiB 기반 혼잡·프레임 제한은 작동하지 않는다 |
| polling과 GPU 자원 | [gpu-worker.mjs](../../native/remote-desktop/gpu-worker.mjs)·[gpu-posix-worker.mjs](../../native/remote-desktop/gpu-posix-worker.mjs)는 2ms polling. Windows는 인코더 입력 최대 3개, 프레임별 NV12 texture/view/sample 생성 | 높은 FPS에서는 대기·할당 비용과 인코더 내부 적체가 더 중요해진다. 상한 3개가 항상 3프레임 지연한다는 뜻은 아니다 |
| 마우스 입력 | [desktop-input.ts](../../src/utils/desktop-input.ts)의 motion은 로컬 커서·버튼 상태에 따라 30/60Hz | 영상만 144fps로 올려도 원격 hover·드래그·스크롤의 갱신은 별도로 제한된다. 버튼과 키는 즉시 reliable 전송이다 |
| 입력 제한 | `native-host.mjs`는 입력 메시지 합계 240개/초 초과 시 종료 | 240Hz motion에는 heartbeat·버튼·키를 위한 여유가 없다. 입력 종류별 예산을 함께 설계해야 한다 |

Windows의 실제 캡처는 WGC다. 공통 개발 문서의 전송 절에 남은 Desktop Duplication 설명을 이 연구의 실행 경로로 사용하지 않는다. 원본 픽셀의 JS IPC나 CPU readback은 Windows/Mac의 현재 주된 경로에서 이미 제거되어 있다. Linux X11은 `ximagesrc`의 CPU 캡처와 GPU 업로드가 남아 있다.

## 바인딩에서 확인한 전송 제약

저장소에 설치된 `node-datachannel` 0.33.4를 별도 Node 프로세스에서 import하고 라이브러리 버전과 prototype을 조회했다. 로컬 Linux 바이너리의 libdatachannel은 **0.24.5**이고, `Track`에 `bufferedAmount()`가 없으며 `PacingHandler`에는 생성자와 `addToChain()`만 있다. 같은 버전의 [Track wrapper](https://github.com/murat-dogan/node-datachannel/blob/v0.33.4/src/cpp/media-track-wrapper.cpp)와 [pacing wrapper](https://github.com/murat-dogan/node-datachannel/blob/v0.33.4/src/cpp/media-pacinghandler-wrapper.cpp)도 이 범위를 확인해 준다. 다른 OS의 설치 바이너리는 구현 전에 같은 조회로 확인한다.

현재 media chain은 H.264 packetizer → Sender Report → NACK responder이고 pacing을 연결하지 않는다. 따라서 큰 프레임의 패킷을 짧은 시간에 몰아서 보낼 수 있다. `Video.setBitrate()`는 SDP 설명이며 실제 인코더·패킷 송출 속도를 제어하는 API와 구분해야 한다.

중요한 함정은 **기존 pacer를 붙이는 것만으로 큐 문제를 해결할 수 없다는 점**이다. [libdatachannel 0.24.5 구현](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.5/src/pacinghandler.cpp)은 RTP 패킷을 내부 queue에 추가하며 큐 상한과 동적 bitrate 변경을 제공하지 않는다. 채널의 buffered amount를 노출하더라도 pacer·OS 소켓·네트워크 적체를 모두 측정한다고 볼 수 없다. bounded queue·프레임 deadline·동적 pacing rate·overflow 복구를 네이티브 전송 계층에 추가하거나, 그 기능을 제공하는 검증된 버전과 바인딩을 연결해야 한다.

## 144Hz 이상 지원 조건

프레임 간격은 60fps에서 16.67ms, 144fps에서 6.94ms다. 입력과 다음 프레임의 위상이 균등하다는 단순 모델에서 한 단계의 평균 대기는 8.33ms에서 3.47ms로 약 **4.86ms** 줄어든다. 이것을 전체 지연 개선량으로 보장할 수는 없지만, 프레임 처리·전송이 따라오면 고주사율 자체도 반응성 개선 수단이 된다.

아래 처리량은 `폭 × 높이 × FPS`로 계산했다. H.264 level 하한은 `ceil(폭/16) × ceil(높이/16) × FPS`와 [ITU-T H.264 2024 Annex A의 MaxMBPS](https://www.itu.int/rec/T-REC-H.264-202408-S/en)를 비교한 값이다. frame size·profile·DPB·프레임률 등의 다른 제약과 실제 decoder 지원도 별도로 만족해야 한다. [RFC 6184](https://www.rfc-editor.org/rfc/rfc6184.html#section-8.1)의 협상 규칙에 따라 SDP와 실제 bitstream을 일치시킨다.

| 검증 목표 | 프레임 간격 | 현재 FHD 60fps 대비 픽셀 처리량 | MaxMBPS 기준 H.264 level 하한 |
| --- | --- | --- | --- |
| FHD 144fps | 6.94ms | 2.40배 | 5.2 |
| QHD 144fps | 6.94ms | 4.27배 | 5.2 |
| QHD 165fps | 6.06ms | 4.89배 | 6.0 |
| 4K 144fps | 6.94ms | 9.60배 | 6.1 |

현재 Level 5.1의 MaxMBPS 983,040은 FHD 144fps의 1,175,040에도 부족하다. QHD 144fps는 Level 5.2의 2,073,600에 정확히 도달한다. FPS 상한을 올리면서 level 광고·실제 encoder 설정·수신 capability를 그대로 두면 정식 지원으로 볼 수 없다. 픽셀 처리량 배수는 필요한 비트레이트 배수가 아니다.

[NVIDIA 공식 성능 표](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/nvenc-application-note/index.html)는 특정 GPU·1080p·인코딩 설정에서 144fps를 넘는 인코더 처리량을 제시한다. 이를 근거로 FHD 144fps를 검증할 가치가 있다고 판단한다. 캡처·색 변환·게임의 GPU 점유·전송·수신 디코드·표시가 포함된 mew 성능을 보장하는 자료는 아니다.

실제 화면이 60Hz로만 갱신되면 동일한 화면을 반복 전송해도 144fps의 정보가 생기지 않는다. 호스트 원본의 갱신율·물리/가상 화면 모드, 수신 기기의 표시 주사율, 해당 해상도/FPS의 하드웨어 디코딩을 함께 확인한다. 144Hz 화면이 있어도 브라우저 전력 정책·백그라운드 상태에 따라 표시율이 달라질 수 있다.

## 고화질에서도 지연을 줄이는 개선 순서

### 실제 큐와 혼잡을 먼저 제어

우선순위가 가장 높다. 프레임을 적당히 나누어 송출하는 pacing, 짧은 시간 예산의 큐, 실제 경로의 혼잡 추정을 하나의 정책으로 묶는다. 인코더 bitrate와 pacer rate를 함께 바꾸며 RTP 헤더·재전송·입력 트래픽의 여유도 남긴다. pacer를 평균 영상 bitrate보다 낮게 고정하면 적체가 계속 증가하고, 지나치게 긴 pacing 간격은 프레임 전달을 늦춘다.

고정 256KiB를 지연 예산으로 쓰는 것도 적절하지 않다. 단순 직렬화 계산에서 256KiB는 6Mbps에서 약 350ms, 20Mbps에서도 약 105ms다. 이는 현재 실제 큐 길이의 측정값이 아니라 `바이트 × 8 / 전송률` 계산이다. 큐 age와 실제 전송 가능률에 맞춘 시간 예산을 사용하고, 오래된 **미인코딩 surface**를 우선 버린다. 이미 인코딩한 참조 P-frame을 버릴 때는 후속 참조 관계를 함께 폐기하고 IDR/SPS/PPS로 복구해야 한다.

현재 feedback은 손실과 jitter-buffer 평균만 전송한다. 수신 FPS·decode 비용·큐 age·경로 RTT 변화·송수신 처리율을 분리해 원인을 판단한다. 100–250ms 정도의 제어 주기를 실험하되, 매 프레임의 React 갱신이나 stats 전체 전송은 피한다. 장기적으로 RTCP 기반 대역폭·도착 시간 feedback을 연결하면 초 단위 제어의 반응 지연을 줄일 수 있다. feedback 주기만 줄이는 것을 완전한 혼잡 제어로 취급하지 않는다.

`decoded: framesDecoded > 0`은 첫 디코드 이후 계속 true이므로 움직이는 화면이 나중에 멈췄는지 판별하지 못한다. 수신·디코드 증분과 호스트의 실제 화면 변경 여부를 비교한다. 정지 데스크톱을 손실로 오인해 계속 keyframe을 요청하지 않도록 구분한다. NACK 캐시 512개와 keyframe 요청의 최소 200ms 간격도 높은 bitrate·RTT의 복구 정책에 맞춰 평가한다.

### 원본 해상도와 고주사율을 협상

브라우저의 수신 코덱 capability, `MediaCapabilities`의 목표 해상도/FPS 평가와 호스트 인코더 capability를 교차 확인한다. 원하는 값·협상한 값·실제 수신 해상도/FPS를 구분한다. 초기 검증은 FHD 120 → 144fps, QHD 60 → 144fps로 진행하고 이후 165fps 이상을 확인한다. 각 OS 검증 조건, wrapper, worker start, SDP bitrate, encoder profile/level과 frame duration을 같은 설정으로 연결한다.

가상 화면의 모드 확장은 [별도 드라이버 계약](../development/remote-desktop-virtual-display.md)의 설치·서명·수명·헤드리스 실기 조건을 따른다. 물리 화면 144fps 경로를 먼저 확인하면 드라이버 작업과 영상 파이프라인 문제를 구분하기 쉽다. 기본 60fps 경로는 capability나 대역폭이 부족한 기기에 유지한다.

### 낮은 지연을 유지하는 인코더 품질 설정

첫 후보는 B-frame 없이 H.264 Main/High 또는 Constrained High를 협상하는 것이다. 현재 Baseline의 호환성 이점을 유지할 fallback을 두고, 더 효율적인 profile에서 같은 화질의 bitrate와 encode 시간을 비교한다. [Apple의 저지연 VideoToolbox 설명](https://developer.apple.com/videos/play/wwdc2021/10158/)도 Constrained High의 압축 효율과 decoder capability 확인을 설명한다. High profile을 쓴다고 자동으로 B-frame이 필요해지는 것은 아니다.

Windows는 `MF_LOW_LATENCY`·`AVLowLatencyMode`·CBR·B-frame 0을 이미 요청한다. 다만 여러 `SetValue()` 결과를 확인하지 않으므로 드라이버가 모두 수락했다고 보장하지 못한다. [ICodecAPI::IsSupported](https://learn.microsoft.com/en-us/windows/win32/api/strmif/nf-strmif-icodecapi-issupported) 등으로 지원을 확인하고 설정 결과와 실제 stream을 검증한다. VBV 크기·preset·QP 정책을 비교하며 가장 느린 고품질 preset을 기본으로 선택하지 않는다.

[NVENC 지침](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/nvenc-video-encoder-api-prog-guide/index.html)은 저지연 용도에 LL/ULL, CBR, 작은 VBV를 제시한다. 작은 VBV는 burst와 지연을 억제하지만 복잡한 화면의 품질 저하를 동반할 수 있어 비교가 필요하다. Linux NVENC의 [GStreamer 설정](https://gstreamer.freedesktop.org/documentation/nvcodec/nvh264enc.html)은 `zerolatency` 외에 `tune`·`vbv-buffer-size`·품질 관련 속성을 별도로 제공한다. mew는 이 값을 명시하지 않는다.

공통 Media Foundation 설정만으로 목표에 도달하지 못하면 NVIDIA NVENC·AMD AMF·Intel VPL의 전용 경로를 비교한다. [AMD AMF API](https://github.com/GPUOpen-LibrariesAndSDKs/AMF/blob/master/amf/public/include/components/VideoEncoderVCE.h)는 저지연 usage·VBV·frame 크기 제어를, [Intel VPL](https://intel.github.io/libvpl/latest/API_ref/VPL_enums.html)은 quality/speed target usage를 제공한다. 전용 API가 모든 GPU에서 더 빠르다는 전제로 대체하지 않고, 인코더가 병목인 기기부터 비교한다.

Mac/Linux의 1초 주기 keyframe과 Windows의 10초 GOP도 큰 압축 프레임의 빈도에 영향을 준다. 복구 속도를 유지하는 범위에서 GOP·요청 IDR·지원되는 intra refresh를 비교한다. 예를 들어 250KB IDR을 20Mbps 경로로 전달하는 데만 약 100ms가 필요하다. 이는 가정한 프레임 크기의 계산이며 실제 mew IDR 크기는 측정해야 한다.

### HEVC와 AV1을 기기별로 선택

높은 해상도에서 같은 화질의 전송량을 줄이면 네트워크 직렬화·적체 비용도 줄일 수 있다. HEVC/AV1의 하드웨어 encode와 decode가 모두 되는 조합을 후보로 삼는다. 소프트웨어 decoder로 바뀌면 압축 효율의 이득보다 지연과 전력 비용이 커질 수 있다.

이미 현재 Node 바인딩에 `addH265Codec`·`H265RtpPacketizer`와 `addAV1Codec`·`AV1RtpPacketizer`가 있다. 새로운 전송 시스템 전체를 만들어야만 코덱을 확장할 수 있는 것은 아니다. 다만 OS 인코더·bitstream format·RTP packetization·SDP·수신 브라우저의 동작까지 구현하고 검증해야 한다.

[Chrome 136 공식 릴리스](https://developer.chrome.com/release-notes/136#h265_hevc_codec_support_in_webrtc)는 WebRTC HEVC 지원을 명시한다. 이것을 모든 OS·브라우저·기기가 해당 해상도/FPS를 하드웨어로 처리한다는 보장으로 사용하지 않는다. codec capability와 `MediaCapabilities`를 조회한 뒤 실제 decoder와 decode FPS를 확인한다. H.264는 호환 경로로 유지한다.

### GPU 자원과 polling 대기를 줄이기

Windows의 NV12 texture·view·sample을 pool로 재사용하되 인코더가 사용을 마친 뒤에만 재사용한다. GPU 캡처 표면 복사도 수명·동기화를 확인한 뒤 줄인다. 현재와 같이 같은 GPU 어댑터에서 캡처·색 변환·인코딩하는 조건을 유지한다.

2ms polling 대신 캡처 FrameArrived와 encoder output event로 다음 작업을 깨우는 경로를 비교한다. 144fps의 6.94ms 예산에서는 여러 단계의 polling 대기가 무시하기 어려워진다. polling 주기만 짧게 만들어 CPU 사용과 전력을 늘리는 방식보다, GPU 작업을 전담하는 스레드와 명확한 surface 수명을 사용한다. Windows의 in-flight 상한 1/2/3과 Mac의 한 프레임 직렬 처리도 처리량·지연을 함께 비교한다.

압축 프레임은 네이티브 출력 → JS Buffer → transferable Uint8Array → RTC Buffer로 여러 번 복사된다. 원본 픽셀 복사보다 비용은 작지만 bitrate가 높아지면 할당·GC 지연을 측정할 가치가 있다. 이후 필요하면 압축 출력을 native packetizer로 직접 전달해 Node를 수명·제어 경로에 집중시킨다.

Linux X11은 GPU 캡처 또는 실제 DMA-BUF import가 가능한 경로를 별도로 평가할 만하다. Wayland에서도 PipeWire를 사용한다는 사실만으로 zero-copy를 보장하지 않으므로 negotiated memory type과 GPU/CPU 복사를 확인한다. Windows·Mac에서 이미 제거한 원본 픽셀 CPU 복사를 다시 주된 개선안으로 제시하지 않는다.

### 입력과 정지 화면 품질을 함께 개선

motion은 입력 중에 120/144Hz 또는 화면·입력 장치에 맞춘 rate로 전송하고, 같은 frame의 여러 이벤트는 최신 위치로 합친다. 로컬 커서의 즉시 표시와 버튼·키의 reliable 전송, 마지막 motion 복구, lease는 유지한다. 호스트 입력 제한은 별도 token budget으로 정리한다. 로컬 커서는 실제 원격 앱의 반응을 앞당겼다는 증거가 아니므로 입력부터 화면 변화까지 따로 측정한다.

문서·코드·터미널에서는 원본 해상도 유지, 글자와 UI 경계의 ROI/QP 조절, 변화가 멈춘 뒤 품질 보강을 평가한다. 움직임이 시작되면 낮은 지연의 갱신 정책으로 복귀한다. Windows/Mac은 이미 변경된 화면 위주로 처리하는 반면 Linux X11은 `use-damage=false`다. 정지 화면을 144번 반복 인코딩하는 방식은 피한다.

현재 NV12 4:2:0에서 작은 유색 글자·서브픽셀 경계의 번짐은 bitrate만으로 해결되지 않을 수 있다. 원본 해상도와 스케일링을 먼저 확인하고, 4:4:4/별도 글자 보강은 브라우저 하드웨어 decode와 구현 복잡도를 검증한 뒤 별도 후보로 다룬다.

## 핑과 화면 반응의 측정

현재 UI의 왕복 시간은 selected candidate pair의 `currentRoundTripTime`이다. [W3C stats 정의](https://www.w3.org/TR/webrtc-stats/#dom-rtcicecandidatepairstats-currentroundtriptime)에 따른 ICE/STUN 경로 RTT이며, 캡처·인코딩·디코딩·모니터 표시 시간이 포함된 값이 아니다. 고화질이 가용 대역폭을 넘으면 적체로 RTT도 커질 수 있지만, 같은 직결 경로에서 화질 설정만으로 전파 지연이 줄어들지는 않는다.

사용자가 체감하는 반응은 입력 전달·원격 앱 처리·다음 화면 갱신·캡처/변환·인코딩·프레임 전송·수신 처리·표시의 영향을 함께 받는다. 다음 값을 같은 구간에서 측정한다.

| 구간 | 측정 값 |
| --- | --- |
| 호스트 | 실제 변경 frame의 capture time, conversion/encode 시간, in-flight, 압축 프레임·IDR 크기 |
| 송신 | pacer queue age/depth, packet/frame deadline 초과, 실제 payload/총 송출률, 재전송량 |
| 수신 | `ΔframesDecoded/Δ시간`, `ΔtotalDecodeTime/ΔframesDecoded`, `ΔjitterBufferDelay/ΔjitterBufferEmittedCount`, freeze/drop |
| 화면 표시 | `requestVideoFrameCallback`의 frame 진행·presentation metadata, 가능한 `framesRendered`, 수신 기기 실제 refresh rate |
| 사용자 반응 | 입력 ID와 화면 변화를 연결한 테스트 장면, 또는 고속 촬영으로 입력 → 실제 화면 변화의 p50/p95 |

`totalProcessingDelay`는 첫 RTP 패킷 도착부터 decode 완료까지의 시간으로 jitter와 decode를 포함한다. 이를 위 수신 값들과 다시 합산하면 중복된다. 브라우저의 frame callback은 실제 모니터 광출력과 같지 않고, 서로 다른 기기의 `performance.now()`를 직접 빼서 단방향 지연으로 보고해서도 안 된다. 현재 Windows timestamp는 캡처 원본 시각 대신 인코더 입력 시각에서 생성하므로 source capture 시각을 보존하는 계측이 필요하다.

현재 `jitterBufferTarget=0` 설정은 이미 적용되어 있다. [W3C WebRTC 계약](https://www.w3.org/TR/webrtc/#dom-rtcrtpreceiver-jitterbuffertarget)상 요청 목표이며 실제 최소 버퍼는 브라우저와 네트워크가 결정한다. 같은 설정을 다시 추가하는 것을 새로운 개선으로 계산하지 않는다.

## 검증 단계와 채택 기준

| 단계 | 작업 | 판단 기준 |
| --- | --- | --- |
| 1 | 기존 FHD 60fps에서 구간별 계측. 실제 codec/decoder·원본 화면 모드 기록 | RTT와 입력 → 화면 지연을 분리하고, 움직이는 장면에서 p50/p95·decode/display FPS 기준선을 확보 |
| 2 | 관측 가능한 bounded pacing·큐 age·feedback 개선, encoder 설정 결과 확인 | 같은 해상도와 bitrate에서 지연·freeze를 비교하고, 대역폭 하락 시 오래된 영상이 누적되지 않는지 확인 |
| 3 | 원본 QHD와 120/144fps 협상, level·duration·motion 연결 | 실제 변경 장면의 수신·표시 FPS가 목표를 따라오며, 기본 60fps 대비 입력 지연과 글자 품질을 함께 개선 |
| 4 | H.264 High·VBV/preset/GOP, HEVC/AV1 비교 | 같은 시각 품질에서 bitrate·encode/decode 지연 비교. 같은 bitrate 비교만으로 우수 판정하지 않음 |
| 5 | GPU resource pool·event 처리·압축 데이터 복사 축소 | 병목인 구간의 p95 개선과 CPU/GPU·전력 비용 확인 |
| 6 | 165/240fps·4K와 가상 모드 확장 | 해당 기기·코덱·실제 stream 제약을 확인한 조합만 지원으로 기록 |

실기 조합은 Windows NVIDIA/AMD/Intel, Mac Intel/Apple Silicon, Linux X11/Wayland를 구분하고 수신 브라우저·GPU·해상도·주사율을 기록한다. 처음에는 실제 사용하는 조합부터 좁혀도 된다. LAN 유선 → Wi-Fi → 외부망 순으로, 정지 글자·스크롤/창 이동·고속 영상 장면을 비교한다. 선택한 조합에서 각 장면을 최소 60초씩 3회 측정하고, 지속 움직임 5분 이상으로 전력·온도·FPS 저하도 확인한다.

대역폭 저하·손실·지터는 격리 환경에서 재현한다. 초기 bitrate sweep의 예로 6/12/20/35/50Mbps를 사용하되, 이는 권장 필요 대역폭이 아니라 비교 입력값이다. 현재 상한 해제와 안정적인 전송 제어가 먼저 필요하다. 글자 crop·시각 비교와 가능한 SSIM/VMAF를 함께 사용하고, 지연 개선은 동일 장면·동일 품질 조건에서 평가한다.

기본 제안은 **현재 직결 구조를 유지하면서 계측과 전송 제어 → 원본 해상도 및 144fps → profile/코덱 → GPU 세부 최적화** 순서다. libwebrtc 전면 교체는 현재 작은 native 전송 모듈을 선택한 [ADR 0185](../../../.mew/docs/decisions/0185-mew-desktop-resident-direct-host.md)의 변경이므로, 앞 단계로 목표에 도달하지 못하고 완전한 혼잡 제어의 이점이 확인될 때 별도 결정으로 검토한다.
