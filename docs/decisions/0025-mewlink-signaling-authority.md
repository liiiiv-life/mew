## 상태

채택. 코드와 격리 검증을 위한 결정이며 운영 반영과 최초 연결 0.5초 달성을 확인한 결정은 아니다. 사용자가 Mewlink 중앙을 재배포해야 적용된다.

후속 [ADR 0028](0028-mewlink-websocket-bootstrap.md)이 HTTP launch만 사용하던 시작 경로와 ticket 이후 RTC 생성 순서를 대체한다. 이 결정의 기기 DO 인가 상태·회수 보존은 유지한다.

## 배경

Mewlink는 첫 접속과 새로고침마다 중앙을 거쳐 직접 WebRTC 연결을 준비한다. 기존 시그널링은 SDP answer·ICE candidate·ready를 처리할 때 기기와 브라우저 회수 상태를 D1에서 반복 조회했다. 연결별 메시지를 순서대로 처리하므로 DB 왕복은 후속 후보의 전달도 늦춘다.

[ADR 0018](0018-mewlink-startup-revalidation.md)은 시작 요청의 중복 왕복과 정적 자원 전송을 줄였지만 중앙 DB 반복 조회는 별도 개선 후보로 남겼다. 이번에는 앱 자원 캐시와 독립적으로 연결 준비 경로의 반복 조회를 줄인다.

## 결정

기기별 `Signaling` Durable Object가 해당 기기의 시그널링 인가 상태를 소유한다. 공개 공유 모듈 `shared/remote-signaling-state.ts`는 기기 메타데이터와 브라우저 registry를 DO의 SQLite 두 테이블에 저장한다. 기존 DO가 처음 이 상태를 요구할 때만 D1의 기기·브라우저 상태를 가져와 초기화하며, 완료한 초기화를 hibernation이나 재연결마다 반복하지 않는다. 초기화와 회수 병합은 동기 트랜잭션으로 처리한다.

SDP answer·ICE candidate·ready는 DO의 영속 기기·브라우저 상태와 WebSocket attachment의 현재 연결·만료·증명을 확인한다. 초기화 이후 중앙 신원을 포함하지 않는 로컬·익명 연결의 이 메시지 처리에서는 D1 조회를 수행하지 않는다. 외부 Mewlink 신원을 포함한 연결의 `authenticateHash` 중앙 세션 검증은 유지한다. WebSocket을 DO에 전달하기 전 Worker의 기기 조회는 존재하지 않는 ID로 DO 저장소를 생성하지 않도록 유지한다.

회수 기록은 해제하지 않는 표시로 남긴다. 초기화 전에 받은 회수, D1에서 읽은 회수, DO에서 직접 처리한 회수를 단조 병합하며, 이후 도착한 활성 상태나 신뢰 등록으로 기기·브라우저를 다시 활성화하지 않는다. 메모리만으로 인가 상태를 보관하거나 유효 기간 동안 낡은 권한을 허용하는 캐시로 대체하지 않는다.

브라우저 관리 목록은 DO registry를 조회한다. 브라우저 접근 해제와 기기 폐기는 DO에 회수 상태를 먼저 저장하고 연결을 닫은 뒤 D1에 사본을 반영한다. D1 반영이 실패해 요청이 오류로 끝나더라도 완료된 DO 회수는 유지한다. 신뢰 브라우저 등록도 회수 기록을 덮어쓰지 않는다.

lease 갱신과 alarm은 D1에서 기기·브라우저 회수를 다시 읽어 DO에 단조 병합한다. 기존 외부 신원의 중앙 세션 검사와 로그아웃 전파도 유지한다. hibernation 후에는 SQLite 인가 상태와 WebSocket attachment를 함께 사용하며, 회수·만료된 연결을 계속 허용하지 않는다.

이 결정은 기기·브라우저 상태의 메시지별 반복 D1 조회를 대체한다. HTTP launch와 일회용 소비, prepare·ready 프로토콜, 서명·키 소유 증명·lease, 직접 P2P 데이터 전송은 유지한다. RTC 프로세스 풀과 자원 캐시는 이번 변경에 포함하지 않는다. 현재 인증·수명·전송 계약은 [원격 접속 계약](../development/remote-access.md#연결-인증과-회수)이 소유한다.

## 근거와 영향

이미 메시지를 중계하는 기기별 DO에 인가 상태를 함께 두면 후보마다 중앙 D1을 기다릴 필요가 없다. DO의 SQLite는 객체별 영속 저장소이므로 메시지 처리와 같은 객체에서 상태를 확인하고 재시작 후 복원할 수 있다. [Cloudflare SQLite 저장 API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)·[WebSocket hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).

기존 native WebRTC 라이브러리를 wrapper로 교체하는 방법은 중앙 DB 왕복을 없애지 않는다. 상시 역터널은 브라우저별 협상을 줄일 수 있지만 작업 데이터가 프록시를 지나므로 현재 직접 전송 계약과 다르다. 이번에는 데이터 경로를 유지하고 확인된 반복 조회를 제거한다.

D1에는 계정·등록·관리 세션·launch와 관리용 사본이 남고, DO에는 시그널링 인가 상태가 추가된다. 운영 D1 스키마 마이그레이션은 필요하지 않다. DO의 두 테이블은 생성 시 준비하며, 기존 기기 등록과 키를 바꾸지 않는다. 중앙 소스는 계속 공개 Git에서 제외하고 공유 상태 모델·검증과 문서만 공개 저장소에 기록한다.

### 백업과 이전 코드로 복구

복구 시에는 D1과 각 DO의 SQLite 상태를 함께 보존한다. D1 반영 실패가 있었다면 DO에만 남은 회수를 D1에도 반영했는지 확인해야 한다. D1만 복원하거나 회수 사본이 누락된 채 D1만 검사하는 이전 코드로 되돌리면 이미 회수한 접근을 다시 허용할 수 있다. DO 상태를 초기화하거나 이전 코드로 복구하기 전에는 두 저장소의 회수를 일치시키며, 더 오래된 활성 상태로 회수 기록을 덮어쓰지 않는다.

## 검증 경계

공유 SQL 모델의 격리 검사 6개는 초기화 1회와 같은 SQLite에서의 복원, 초기화 전 회수 보존, 기기·브라우저별 격리, 신뢰 등록의 회수 부활 차단, D1 회수의 단조 병합과 초기화 실패 시 트랜잭션 롤백을 확인했다. 중앙 Workers 검사 66개도 통과했다. 새 성능 검사는 ready·양방향 ICE 후보 40개·answer 전달에서 기기·브라우저 D1 조회 0회, 외부 신원 세션 검사 유지, hibernation 복원과 관리 API의 D1 갱신 실패 뒤 회수 유지를 확인한다. 루트·중앙 타입 검사, 루트 lint와 문서 검사도 통과했으며 기존 lint 경고는 남아 있다.

실제 Workers·네이티브 RTC·Chromium을 사용하는 P2P 브라우저 검사 2개도 통과했다. 로그인·앱 자원·새로고침과 정상 WS 메시지 1000개·혼합 HTTP 전송, 브라우저 갱신 타이머가 멈춘 상태의 65초 이상 lease 유지, 로컬 비밀번호 회수와 기기 폐기 후 앱 프레임 제거를 확인했다. 동일 호스트의 격리 검사이며 운영 외부망 실측은 아니다.

Workers/D1/DO 통합 검증과 운영 적용은 구분한다. 최초 연결 0.5초는 목표이며 이 변경의 달성 수치로 기록하지 않는다. 사용자 재배포 뒤 자원 캐시가 없는 첫 방문·새로고침을 각각 측정하고 중앙 왕복·ICE·DTLS·DataChannel 인증·앱 표시 시간을 나눠 확인해야 한다. 실제 외부망·휴대폰·NAT별 연결 성공률과 지연은 별도 검증 대상이다. 에이전트는 앱 빌드·서버 재시작·중앙 배포를 실행하지 않는다.
