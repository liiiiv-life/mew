# 0016 — Hotview 블록 캐시와 Pretext 기반 DOM 가상화

상태: 채택

## 배경

[도입 전 측정](../research/editor-input-performance.md)에서 1.13MB 합성 Markdown의 Hotview 입력은 키당 JavaScript 약 16초를 사용했다. 전체 문서 직렬화가 입력마다 4회 반복되며 대부분의 시간을 썼다. 화면 밖 문단의 텍스트 DOM과 링크 커서 장식도 유지되어 문서가 길수록 갱신 비용이 커졌다.

## 결정

1. 기존 Markdown 렌더러를 사용하는 블록별 직렬화 캐시를 도입한다. 저장 통지를 지연하지 않으며 기존 문자열·클립보드 형식을 보존한다.
2. 줄 번호를 plugin state와 블록별 line map으로 관리한다. 로컬 입력의 React echo와 커서 이동에서 전체 직렬화·Markdown 분석을 반복하지 않는다.
3. Pretext 1.0.0을 에디터 패키지 의존성으로 고정한다. 텍스트 높이를 예측하고 화면 밖 최상위 블록의 내용 DOM을 자리표시자로 대체한다. 화면에 나타난 뒤 실제 높이로 보정한다.
4. 문서 모델·Yjs·undo 이력은 전체를 유지한다. 선택·조합 중인 블록은 표시하고, 탐색 시 모델 위치에서 DOM을 복원한다.
5. 표시 범위에 필요한 줄 번호·파일 링크 커서 장식만 ProseMirror에 전달한다. 가상화의 보조 계산 자체가 문서 길이의 제곱으로 늘어나지 않도록 위치·측정 캐시를 사용한다.

## 근거와 영향

Pretext는 직렬화 비용을 해결하지 않으므로 캐시와 표시 범위 제한을 함께 적용한다. 단순 CSS 숨김은 DOM·노드뷰 생성과 장식 계산을 줄이지 못해 채택하지 않았다. 전체 편집 모델을 부분 문서로 교체하는 방식은 협업·선택·undo의 위치 계약을 바꾸므로 사용하지 않는다.

문서가 짧으면 기존 전체 표시를 유지한다. 큰 문서도 최상위 블록별 자리표시자는 남는다. 거대한 단일 목록·표의 내부와 긴 선택 범위는 충분히 많은 DOM을 만들 수 있다. 글꼴·복잡한 노드의 예측 오차는 측정과 스크롤 앵커 보정으로 줄인다. 화면 밖 텍스트의 브라우저 자체 찾기와 접근성 트리 상주는 제한된다.

현재 계약과 검증 경계는 [Hotview 렌더링](../development/hotview-rendering.md)에 둔다. 앱 빌드·서버 반영과 실제 OS 키보드 확인은 격리 테스트 통과와 구분한다.
