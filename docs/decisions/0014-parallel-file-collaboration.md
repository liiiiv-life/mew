# ADR 0014: 파일 조회와 협업 연결 병렬 준비

## 배경

[ADR 0013](0013-file-content-revalidation.md)은 캐시를 읽기 전용으로 먼저 표시하고 파일 본문·권한 확인 뒤에 협업을 시작한다. 이 순서에서는 본문 요청과 협업 접속 대기가 직렬로 누적된다. 캐시 전송량을 줄여도 처음 여는 글의 두 대기는 남는다.

## 결정

로그인 사용자가 활성 주 편집화면에서 여는 일반 파일은 본문 요청과 협업 연결을 병렬로 준비한다. 소켓은 기존 서버의 협업 기능·파일 편집 권한 검사를 그대로 받는다. 확인 전의 Y.Doc은 편집기에 전달하지 않으며 로컬 본문으로 시딩·편집·자동 저장하지 않는다. 파일 응답이 본문과 편집 권한을 확인하면 그때 연결한다. 조회 실패·편집 불가·탭 전환·언마운트는 연결을 정리한다.

게스트·미디어·외부 파일·아카이브·비활성 복원 탭·anchor preview에는 적용하지 않는다. 협업 소켓이나 비활성 편집기의 풀을 만들지 않는다. 와이어 형식과 서버 권한·저장 계약도 유지한다. ADR 0013의 캐시 확인 전 수정·시딩 금지는 유지하며 연결 준비 순서만 보완한다.

협업 훅은 현재 프로젝트·경로·계정과 일치하는 문서만 반환한다. Hotview는 협업 문서가 바뀌면 React key로 편집기를 새로 마운트한다. 동기화가 파일 응답보다 빠른 경우 폐기된 기존 편집기를 시딩하는 경합을 방지한다.

## 비교한 방법

- 캐시·조건부 본문 조회: 이미 적용했으며 재방문 전송량을 줄인다. 콜드 오픈의 협업 대기는 남는다.
- hover 프리패치: 클릭 전에 미리 준비할 수 있지만 터치 입력에는 이득이 작고 읽지 않을 파일의 요청이 늘어난다. 이번에는 적용하지 않는다.
- 비활성 협업 편집기 유지: 재방문 생성 비용을 줄이지만 방·소켓·메모리 수명과 기존 풀링 금지 결정을 바꿔야 한다. 이번에는 적용하지 않는다.
- 활성 파일의 병렬 준비: 요청 대상 수를 늘리지 않고 두 네트워크 대기를 겹칠 수 있어 선택했다. 다만 확인 결과 편집 불가인 파일은 준비 접속 한 번이 추가될 수 있다.

## 검증 경계

`server/editor-file-cache-ui.test.ts`는 확인 전 캐시 읽기·수정 차단·협업 update 프레임 부재, 확인 후 연결·편집, 외부 변경·권한 회수와 준비 연결 정리를 검증한다. 재연결 검사는 `server/collab-reconnect-ui.test.ts`가 소유한다.

`server/file-open-performance-benchmark.mjs`는 실제 공개 주소 접속 상태와 합성 지연 실험을 별도로 출력한다. 합성 실험은 브라우저 요청을 가로채 별도 예제 문서·HTTP·WebSocket 응답을 사용한다. 배포된 사이트의 로그인 후 실제 글 열기 결과가 아니다. 운영 빌드·재시작은 수행하지 않으며, 로그인과 사용자 적용 후 운영 성능 검증은 남는다.
