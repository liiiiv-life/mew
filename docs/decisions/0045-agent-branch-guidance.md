## 상태

채택.

새 worktree의 기본 위치와 중복 탐색 제외·안내 버전 호환은 [후속 결정 0054](0054-internal-worktrees.md)를 따른다.

자동 처리 범위와 해당 선택이 부여하는 커밋·병합·원격·정리 권한은 [후속 결정 0046](0046-agent-git-automation.md)이 확장한다. 아래 권한 제한은 기존 수동 모드의 기준으로 유지한다.

## 배경

기존 기본 지침은 커밋 시점을 설정했지만 작업 브랜치를 분리하는 흐름은 안내하지 않았다. 그 결과 기본 브랜치에 변경이 계속 쌓일 수 있었다. Mew는 개인·협업 프로젝트와 GitHub에 연결하지 않은 로컬 저장소도 다루므로 하나의 배포 방식이나 원격 서비스를 모든 프로젝트에 강제할 수 없다.

## 결정

계정별 기본 지침에 Git 브랜치 전략과 세부 설정을 추가한다. 기본은 GitHub Flow 계열의 짧은 작업 브랜치이며, Git Flow·Trunk 기반·프로젝트 지침에 따름을 선택할 수 있다. 기본·개발 브랜치·접두사·worktree 사용·승인된 병합 방식·통합 후 정리 선호를 GUI에서 조정한다. 전략과 세부 값은 하나의 저장 동작으로 함께 반영한다. 구체적인 선택값과 동작은 [기능 계약](../features/프로젝트·파일·검색/프로젝트%20문서%20안내·초기화.md)과 [사용 안내](../guides/project-setup.md#git-브랜치-지침)가 소유한다.

설정은 매 ACP 요청에서 에이전트에 전달하는 지침이다. Mew가 저장소를 자동 전환하거나 원격 보호 규칙을 설치하지 않는다. 커밋·push·PR·병합·삭제의 권한은 기존 사용자 요청·프로젝트 지침·커밋 설정을 따른다. 병합 방식과 정리 설정도 권한을 추가하지 않는다.

기존 지침에 브랜치 구간이 없으면 읽을 때 기본 안내만 보충한다. 원문을 덮어쓰지 않고 직접 편집한 구간을 보존한다. 작업 전 저장소와 기존 브랜치·미커밋·스테이징 상태를 확인하고 관련 작업 브랜치를 재사용하도록 안내한다. 공유 체크아웃이나 변경 충돌 위험에는 worktree를 권하되, 기존 미커밋 변경이 새 worktree로 자동 이전되지 않는다는 경계를 유지한다.

## 근거

| 전략 | 공식 자료의 적용 조건 | Mew의 선택 |
| --- | --- | --- |
| GitHub Flow | 작업을 짧고 설명적인 브랜치로 분리하고 검토 뒤 기본 브랜치로 통합한다. 관계없는 변경은 브랜치를 나눈다. | 기본 브랜치의 작업을 분리하려는 요구에 맞고 별도 개발·릴리스 브랜치가 항상 필요하지 않아 기본으로 채택한다. 원격 push·PR 실행은 기존 권한을 따른다. |
| Git Flow | 개발과 배포 브랜치를 유지하며 릴리스·긴급 수정을 구분한다. 저자는 지속 제공에는 단순한 흐름을, 명시적 버전·여러 운영 버전 지원에는 Git Flow를 제안한다. | 여러 버전과 계획된 릴리스를 관리하는 프로젝트를 위한 선택지로 제공한다. |
| Trunk 기반 | 작은 변경을 빠르게 통합하고 짧은 작업 브랜치와 신속한 검토·CI를 사용한다. | 프로젝트의 검증·통합 체계에 맞춰 명시적으로 선택한다. |

위 비교는 [GitHub Flow 공식 안내](https://docs.github.com/en/get-started/using-github/github-flow), [Git Flow 원저자 글과 2020 회고](https://nvie.com/posts/a-successful-git-branching-model/), [Trunk Based Development의 짧은 작업 브랜치 안내](https://trunkbaseddevelopment.com/short-lived-feature-branches/)를 2026-10-22 확인한 결과에 따른다. 기본값 선택은 이 자료와 Mew의 로컬·에이전트 작업 범위를 바탕으로 한 프로젝트 판단이다.

## 영향

기본 지침을 쓰는 기존 계정도 다음 요청부터 브랜치 분리 안내를 받으며, 기존 MD와 프로젝트 지침은 유지된다. 프로젝트 자체 규칙을 우선해야 하면 프로젝트 지침에 따름을 선택한다. GitHub Flow라는 이름을 사용해도 GitHub 연결이나 원격 작업을 필수로 요구하지 않는다. 별도 worktree를 선택한 작업은 해당 폴더와 필요한 실행 환경을 확인해야 하며, 브랜치를 생성하는 것만으로 기존 공유 폴더의 변경이 격리되지는 않는다.
