## 상태

채택. 구현과 격리 검증 뒤 중앙 런처·로컬 실행본을 각각 적용한다. 원격망 전체의 성능이나 로딩시간 목표 달성을 보장하지 않는다.

## 배경

대형 WebSocket 메시지에는 HTTP와 같은 수신 credit가 없어 빠른 호스트가 브라우저 수신 작업을 미리 채웠다. 동일 호스트의 실제 네이티브 RTC·MessagePort 두 단을 거친 22.5MB 혼합 부하에서 작은 WS와 HTTP가 수백 ms씩 늦어졌다. 격리 수신 제어 실험은 전체 CPU 점유가 비슷한 상태에서도 이 지연을 줄였다.

반면 HTTP의 기존 8청크·96KiB 창을 큰 전송에도 고정하면 먼 네트워크에서 왕복마다 기다려야 한다. 지속 소켓이 공통 슬롯 16개를 모두 점유하면 작은 HTTP도 소켓이 닫힐 때까지 기다린다.

## 결정

기존 v1과 `responseWindow`의 1~8청크 계약은 유지한다. 새 상대끼리는 선택 필드 `flowControl`을 요청·응답 또는 소켓 열기로 협상하고, 확인한 상대에만 배치 credit와 확장 수신 창을 사용한다. 협상하지 않은 상대에는 기존 HTTP 수신 창과 WS 전송을 유지한다.

처음에는 8청크만 허용한다. 최종 소비자가 데이터를 처리한 뒤 왕복시간과 청크 처리 비용에 따라 창을 조절하며, 출력 큐에 남은 바이트와 이미 허용한 credit를 함께 계산한다. 읽지 않는 HTTP의 초기 자동 pull을 실제 소비로 취급하지 않는다. credit는 소비 배치 뒤 다음 작업으로 미뤄 보내 UI와 다른 작업이 실행될 기회를 준다. 각 창은 최대 256청크·3MiB를 넘지 않는다.

앱·런처·중앙 부모의 MessagePort 브리지는 최종 소비자의 credit를 그대로 전달한다. 중간 브리지가 자체적으로 소비 완료를 인정하거나 credit를 추가하지 않는다. 취소·닫기·권한 회수는 창 대기를 해제하며 늦은 credit가 새 작업을 열지 않는다.

같은 협상의 선택 기능으로 지속 WS와 HTTP의 admission을 분리한다. 각 종류는 16개, 채널 합계는 최대 32개다. 협상 전과 구버전에는 공통 16개를 유지한다. 같은 종류의 대기 순서는 보존하며 막힌 소켓 때문에 비어 있는 HTTP 슬롯이 놀지 않도록 한다. 기존 바이트·메시지·업로드·대기열 한도와 인증 검사는 유지한다.

Base64 형식은 호환을 위해 유지하되 지원 브라우저의 네이티브 변환을 사용한다. 미지원 환경은 단순 반복으로 변환하며 프레임 검증은 기존 허용 형식을 유지한다. [표시용 도구 이벤트](0031-agent-display-events.md)로 전송량을 줄이는 변경과 함께 적용한다.

## 근거와 영향

고정된 작은 WS 창만 도입하는 대신 지연·소비·CPU 비용에 상한을 둔다. 새 기능은 상대가 확인한 경우에만 사용하므로 중앙·앱·호스트의 적용 순서가 달라도 기존 연결이 가능하다. 단일 ordered DataChannel과 메시지 순서·최종 조립 의미는 바꾸지 않는다.

공통 전송 계약과 구체 검증 결과는 [원격 접속](../development/remote-access.md), 중앙 적용은 [배포 계약](../deployment/remote-central.md)이 소유한다. 프로토콜의 임의 바이트 압축이나 원시 도구 상세 조회는 이 결정에 추가하지 않는다.
