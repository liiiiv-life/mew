# 문서 작성·탐색 규칙

사용법을 찾는다면 [전체 문서 홈](MOC.md) 또는 [사용법 홈](guides/MOC.md)에서 시작하세요. 이 문서는 문서를 쓰거나 유지하는 사람과 에이전트의 규칙입니다.

Mew의 기준 문서는 이 `docs/`에 둔다. [독립 프로젝트 결정](decisions/0001-independent-project.md)에 따라 지침·문서·결정·검증을 이 저장소가 소유한다. 부모 Liiiiv 지침이나 중앙 문서의 탐색·갱신·등록은 요구하지 않는다. 문서 탐색은 [이전 ADR 0199](history/decisions/0199-mew-description-discovery.md)의 description 방식을 유지한다.

## 필요한 문서 찾기

프로젝트 README·지침과 [실행·검증 규칙](development/getting-started.md)을 먼저 읽는다. 이후 문서 경로와 YAML 프론트매터 `description`만 훑어 필요한 current 문서 본문을 선택한다. description은 탐색 힌트이며 정확한 사실·상태·계약은 선택한 본문에서 확인한다. 문서 본문·history·연구 원문을 통째로 로드하지 않는다.

저장소 루트에서 아래 명령은 본문을 출력하지 않고 경로와 description을 동적으로 나열한다. 별도 목록 파일의 관리나 색인이 필요 없다.

```bash
node server/document-descriptions.ts
npm run check:docs
```

기본 목록은 `history/`·`archives/`·숨김 경로·심볼릭 링크를 제외한다. 과거 근거가 필요할 때만 `--all`로 history 설명을 포함한다. archives는 항상 읽기 전용이며 목록에서도 제외한다. 설명이 없는 문서·빈 문자열·잘못된 YAML·옛 `desc` 키는 검사 오류다.

## 문서 배치

| 내용 | 기준 위치 |
| --- | --- |
| 사용자 설치·조작 | `guides/` |
| 기능별 요구사항·상세 동작·확인 기준 | `features/`의 해당 기능 파일 |
| 공유 구현·저장·통신·UI·검증 계약 | `development/` |
| 설정·환경변수·외부 도구 연결 | `configuration/` |
| 서버 설치·배포 | `deployment/` |
| 반복 운영·보안·접근·복구 | `operations/` |
| 기술 선택·공유 계약·기존 결정 변경 | `decisions/` |
| 태스크 제목·완료·태그·기간 | `tasks/`의 개별 작업 파일 |
| 설계·조사·구현 및 적용 검증 기록 | `work/` |
| 비교·실측·연구 원문 | `research/` |
| 대체된 구현·제거된 기능·이전 계약 | `history/` |

작업 기록의 검증 성공과 실제 운영 적용은 구분한다. 완료 여부나 현재 계약을 제목·수정일만으로 추정하지 않는다. 대체된 구현 기록은 현재 기준본을 확인한 뒤 `history/`로 옮기며, 원문과 미검증 조건을 보존한다. 들어오는 링크를 보정하고 기존 결정·외부 링크가 사용하는 경로는 필요하면 짧은 이동 안내로 유지한다. 연구 원문은 `research/`에서 보존하되, 이전 구현에 대한 연구는 문서 홈에서 History / raw로 구분한다.

문서를 정리할 때는 먼저 내용의 소유권을 확인한다. 같은 주제를 다뤄도 사용법·설정·구현 계약·작업 기록은 독자가 찾는 정보가 다르다. 기준이 겹치는 내용은 기존 소유 문서에 모으고 다른 문서는 연결한다. 파일을 `docs/` 바로 아래로 옮기는 것만으로 분류를 마치지 않는다.

태스크의 상태·기간·태그·담당자는 태스크에 남기고 긴 설계·구현·검증 기록은 `work/`로 분리한다. 기록과 연구에는 관찰 시점과 현재 기준본을 밝혀 당시의 미구현·미배포·제약을 현재 상태로 읽지 않게 한다. 중복 문단을 정리할 때는 고유 내용·수치·코드·체크박스·미검증 조건을 보존한다. 나이나 파일명만으로 기록을 폐기하지 않는다.

## 상위파일

상위 문서 안내는 본문에 쓰지 않고 프론트매터 `상위파일`에 현재 문서 기준 상대 경로로 기록한다. 하나면 문자열, 여러 문서로 연결하면 문자열 배열을 쓴다. 본문에는 하위파일 목록과 내용상 필요한 참조 링크를 둔다. 기능 문서의 기존 `parent` ID는 별도 필드이며 변경하지 않는다.

## description 작성

모든 docs Markdown의 첫 YAML 블록에 비어 있지 않은 문자열 `description`을 쓴다. 대상 기능·계약·문제와 문서가 다루는 범위를 1\~2문장으로 적는다. 제목만 반복하거나 본문 전체를 복제하지 않는다. 미구현 계획·이전 계약·이동 안내·연구 결과는 그 성격을 명시해 현재 구현과 구분한다. 필드 이름은 `description`으로 통일한다.

새 문서나 상세 본문을 작성할 때 설명을 함께 쓴다. 태스크 패널에서 제목만 추가한 문서는 `태스크: 제목`으로 시작하며 제목을 바꾸면 자동 기본 설명도 따라간다. 직접 다듬은 설명은 패널이 덮어쓰지 않는다. 본문 범위·상태가 바뀌면 작성자가 설명도 갱신한다.

## 소유권과 갱신

기능 전용 요구사항·상세 명세는 해당 기능 파일이 소유하고, 여러 기능이 공유하는 개발 계약·사용법·운영은 기존 소유 문서에 둔다. 코드·기능·운영 변경과 소유 문서 갱신은 같은 작업에서 한다. 기술 선택·공유 계약·기존 결정 변경은 [Mew 결정 기록](decisions/README.md)에 남긴다. 이관한 중앙 ADR은 `history/decisions/`의 이력으로 보존하며 현재 규칙은 Mew 문서에서 정한다. 시크릿과 임시 디버깅 로그를 문서에 쓰지 않는다.

새 문서를 만들거나 옮길 때 MOC에 등록할 필요는 없다. 실제로 존재하는 들어오는 링크는 이동·개명과 함께 보정한다. 기존 MOC·대표 문서는 Documents·기능 화면과 이전 링크의 호환을 위해 보존한다. MOC의 링크 목록은 모든 파일을 망라하는 필수 인덱스가 아니다. history의 원래 본문·연구 결과는 보존하고 archives는 수정하지 않는다.

`npm run check:docs`는 description과 저장소 내부 링크를 검사한다. 링크의 상대 경로는 저장소 안에 있어야 하며 다른 로컬 프로젝트의 파일을 필수 참조로 연결하지 않는다. 공개 저장소에서 제외한 소스·설정 파일은 경로를 코드로 표기하고 별도 준비 조건을 설명한다. 과거 문서의 옛 경로 표기는 이력으로 보존하되 클릭하는 근거 링크는 이관본으로 연결한다. 상세 Markdown은 내용에 맞는 `docs/` 하위 폴더에 두고, 저장소 루트에는 `README.md`·`AGENTS.md`·`CLAUDE.md`를 둔다. 스킬·패키지의 전용 문서는 기존 형식을 유지한다.

현재 링크 검사는 대상 파일의 존재와 저장소 경계를 확인하며 `#` 뒤의 목차 위치는 검사하지 않는다. 제목이나 명시적 앵커를 바꾸면 같은 문서의 목차와 다른 문서의 들어오는 링크도 확인한다. 기존 언어판이 공통으로 쓰는 고정 앵커는 유지하거나 참조를 함께 보정한다.

## 읽기 쉬운 안내 작성

- 소개는 용도·대표 화면·시작 링크를 먼저 보여준다. 설치 안내에 전체 기능 명세를 반복하지 않는다.
- 시작 안내는 준비 조건 → 설치 → 첫 로그인 → 첫 작업 순서로 쓴다. 현재 가능한 설치와 미발행 릴리스를 구분한다.
- 사용법은 하려는 작업·시작 위치·결과를 설명하고, 구현 계약과 검증 근거는 소유 문서로 연결한다.
- 분야 홈은 주제별로 묶어 연결한다. 현재 사용법·계약을 먼저, 작업·연구·이력은 성격을 명시해 뒤에 둔다.
- 화면 이미지는 `assets/screenshots/`에 두고 상대 링크와 구체적인 대체 텍스트를 쓴다. 기본 촬영 조건은 **기본 미드나이트 테마와 뮤펫 표시**다. 다른 테마나 숨김 상태를 설명할 때만 해당 조건을 바꾼다.
- 실제 실행 중인 UI를 촬영한다. 새 브라우저 컨텍스트에서 예제 데이터를 사용하고, 촬영일·화면 크기·모의 응답 사용 여부·실기기 여부를 이미지를 소개하는 문서에 기록한다. 계정·개인 파일·대화·시크릿을 포함하지 않는다. 촬영을 위해 앱을 빌드하거나 서버를 재시작하지 않는다.
- 같은 내용의 언어판은 핵심 순서와 범위를 맞춘다. 기존 헤딩 앵커나 참조 경로를 바꾸면 들어오는 링크도 확인한다.

소개·설치·상세 안내를 나누는 구성은 [code-server README](https://github.com/coder/code-server)와 [HedgeDoc 문서 홈](https://docs.hedgedoc.org/), 기능을 중심으로 소개하는 방식은 [AFFiNE README](https://github.com/toeverything/AFFiNE)를 참고했다. mew의 폴더 소유권과 description 탐색 규칙을 그대로 따른다.
