# Mew 기능 문서 관리

[기능 지도](MOC.md)에서 분야를 고른다. **Mew 프로젝트 탭을 열고 메뉴 → 기능**에서도 같은 문서들을 읽는다. Liiiiv 상위 프로젝트의 기능 목록과는 별개다. Mew의 Documents 연결은 `docs`를 사용한다.

## 기준본과 탐색

- 기능 문서는 **작업 단위·제품 범위·관련 구현 진입점·사용자 확인 기준**을 소유한다. 파일명과 무관한 `mew-<분야>-<기능>` ID와 `parent`로 계층을 유지한다.
- 기능을 맡길 때 해당 기능의 내용과 연결한 **상세 계약**을 함께 읽는다. `guides/`는 조작 절차, `configuration/`은 설정, `development/`는 실행·API·저장 계약, 기존 `specs/`는 세부 UI·행동 계약을 계속 소유한다. 상세 본문을 기능 문서에 복제하지 않는다.
- 코드나 기능이 바뀌면 해당 기능 문서와 변경 사실을 소유한 상세 계약을 같은 작업에서 갱신한다. 실행 방법·검증 명령은 프로젝트 README, 결정 근거는 중앙 ADR에 남긴다.
- 상위 기능은 분야의 범위를 묶는다. 개별 구현 요청은 가능한 한 가장 구체적인 하위 기능에 맡긴다. 상위의 상태로 모든 자식이 승인됐다고 판단하지 않는다.

## 최초 목록화의 상태

2026-09-18 기준 8개 상위 기능과 44개 하위 기능을 등록했다. `created`는 기능 문서의 등록일이며 실제 최초 구현일이 아니다.

- 현재 제공 범위가 문서와 구현 진입점에서 확인된 항목은 `implemented`(민트·사용자 확인 전)로 등록했다. 모든 환경에서의 동작 검증 완료를 뜻하지 않는다.
- 사용자 승인 없이 `verified`(초록)나 사용자 수정 판정인 `needs-fix`(빨강)를 넣지 않는다. 각 문서의 검증 부분은 **앞으로 사용자가 확인할 항목**이며 이번 정리에서 수행한 실서비스 테스트 결과가 아니다.
- `status_hash`는 현재 요구사항 내용에 상태를 연결하는 값이다. 일반 편집 뒤 해시를 그대로 두면 GUI에서 주황으로 표시된다. 정리 후 변경에 기존 구현 판정을 기계적으로 다시 붙이지 않는다.
- `files`는 실제 구현의 대표 진입점이며 변경 파일 전체 목록이 아니다. 과거 실행·커밋을 추정하지 않아 `commits`는 비워 두었다. 서버 요청 이력은 새로 만들지 않았다.

## 새 기능과 수정

기존 ID를 유지해 기능을 수정한다. 새 기능은 GUI에서 요청하거나 [저장 형식](../specs/feature-development.md)에 맞게 파일을 추가하고 부모 ID와 가까운 MOC 링크를 함께 작성한다. 새 문서를 직접 추가할 때는 `changed`를 사용하고, 아직 없는 동작을 구현 완료로 등록하지 않는다.

일반 설명·인덱스는 예약된 `README.md`·`MOC.md`를 사용한다. 이 두 파일은 기능 항목으로 읽지 않는다. 폴더 이름이 GUI 부모 관계를 결정하지는 않는다. 파일 이동 시 상대 링크·MOC와 `parent`의 의도를 별도로 확인한다.

기능에 연결된 실행 중 에이전트는 공통 CLI의 assign/report 경로를 사용한다. 문서만 편집해도 자동 실행이나 Git 커밋은 발생하지 않는다. 서버 원장·큐·이전·복구 계약은 [기능 기반 개발](../specs/feature-development.md)에 둔다.

## 목록에 넣지 않은 것

옛 홈의 할 일·달력, 미구현 AI 커밋 메시지 생성, 실현되지 않은 계획을 현재 기능으로 만들지 않았다. 의미 검색은 공통 RAG 패널·서버 API·에이전트 안내 범위, Android는 환경 준비와 기존 gateway 연결 범위로 등록했다. 설치·HTTPS·백업·라이선스·연구·과거 계획은 별도의 기능 항목으로 복제하지 않고 기존 소유 문서에 유지한다.
