- 결정자: 사용자 (설계 방향·구현 승인), Codex (구현)

## 배경

완료 턴마다 전체 JSON을 재작성하고 접속마다 전체 전사를 보내는 비용이 대화 길이에 비례해 증가한다. 서버 복원 전사와 공급자 ACP 기록의 역할은 유지하며 저장·조회·전송 단위를 줄인다.

## 결정

- 서버 로컬 DATA_DIR의 SQLite WAL에 세션별 순번과 이벤트를 저장한다. 일반 저장은 새 이벤트만 추가하고 ACP 복원으로 내용이 바뀌면 트랜잭션으로 교체한다. 작은 설정 JSON은 유지한다.
- 기존 v2 JSON은 검증 후 최초 조회 시 이전하며 삭제하지 않는다. SQLite 오류를 빈 기록으로 덮어쓰지 않는다. 공급자 기록과 기존 복원 실패 보호는 유지한다.
- 감독 수명/전사 교체별 generation과 순번으로 최근 구간·이전 구간·재접속 변경분을 식별한다. 세대 불일치·불완전 캐시는 최근 구간으로 다시 동기화한다. 질문/답변 경계를 보존하고 CLI 배치는 전체 질문 오프셋을 사용한다.
- 계정 서버 탭 원장을 확인한 뒤 동일 세션의 IndexedDB 기록은 연결 전에도 실제 버블로 표시한다. 예전 localStorage 줄글 미리보기와 원장 조회 전 연결 금지는 유지한다.
- 새 감독은 구간 전송을 협상하며 기존 감독/클라이언트의 전체 replay 경로를 호환한다. 조회는 기존 인증된 탭 연결 안에서만 가능하다.
- 브라우저는 계정·탭·런타임·cwd로 격리한 IndexedDB에 최근 기록을 비동기 저장한다. 용량·기간을 제한하며 저장 실패는 실시간 대화를 막지 않는다. 초안·설정은 기존 저장 계약을 유지한다.
- 빌드·배포·실제 기록 이전은 사용자가 변경을 적용한 뒤 발생한다. 구현 작업은 격리된 테스트 데이터만 사용한다.

## 근거

별도 DB 서비스를 설치하지 않고 부분 조회와 원자적 갱신을 제공한다. 전체 JSON을 DB 한 행에 저장하는 방식은 조회·직렬화 비용을 해결하지 못한다. SQLite WAL은 같은 호스트의 읽기/쓰기 동시성을 제공하지만 쓰기는 직렬화되므로 짧은 트랜잭션과 busy timeout을 사용한다.

현재 계약과 검증은 [대화 저장](../../development/conversation-storage.md), 진행 기록은 [구현 계획](../../work/conversation-storage.md)을 따른다.
