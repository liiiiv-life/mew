- 결정자: 송상훈 (지시)

## 배경

루트 프로젝트를 오갈 때 서버가 watcher·협업 방·에이전트 세션을 정리한 뒤 브라우저 전체를 새로고침했다.
서버의 활성 루트가 프로세스 전역 하나라는 제약은 유지되지만, 새로고침은 이미 브라우저에 있는 화면 껍데기와
최근 탭·본문 캐시까지 버려 전환 체감 시간을 키운다.

## 선택지

1. 전환마다 전체 새로고침을 유지한다 — 상태 경계는 단순하지만 화면과 캐시를 매번 다시 만든다.
2. 서버 전환 뒤 SPA에서 루트별 상태를 교체한다 — 현재 서버 제약은 유지하면서 재기동 비용을 없애지만 캐시 키를 루트별로 분리해야 한다.
3. 여러 루트 서버 컨텍스트를 동시에 유지한다 — 백그라운드 실로딩은 가능하지만 watcher·협업·에이전트 경계를 크게 재설계해야 한다.

## 결정

- 서버는 한 번에 루트 프로젝트 하나만 활성화하며 기존 watcher·협업 방·에이전트 정리 절차를 유지한다.
- `workspace` presence 신호를 받으면 클라이언트는 새로고침하지 않고 현재 루트 정보와 트리를 다시 읽어 화면을 교체한다.
- `.workspace`와 `docs`의 API 식별자는 유지하되, 열린 탭 목록과 파일 본문 캐시는 루트 절대 경로를 포함한 키로 분리한다.
- 루트를 바꾸면 서버가 폐기한 에이전트 UI는 닫고, 새 루트의 탭 상태를 복원한다. 탭 내용은 기존의 작은 텍스트 LRU 한도를 계속 따른다.
- 다른 루트의 실제 서버 트리·파일을 백그라운드에서 읽지는 않는다. 전역 활성 루트를 바꾸지 않고 이를 하려면 선택지 3의 별도 서버 컨텍스트가 필요하다.

## 근거

작은 탭 목록과 텍스트 본문 캐시는 제한된 브라우저 저장소 안에 남겨도 비용이 작다. 반면 전역 서버 루트를 미리 바꾸는 방식은 현재 사용자가 보는 watcher·협업·에이전트 상태를 끊어 버리므로 안전하지 않다.
