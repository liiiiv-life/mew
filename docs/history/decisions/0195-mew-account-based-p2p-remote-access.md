## 배경

설치자마다 도메인·터널을 구성하거나 접속 기기마다 VPN을 설치하면 셀프호스팅 mew를 어디서나 쓰기 어렵다. 사용자는 서버 A만 한 번 등록하고, 임의의 브라우저 B·C·D에서 같은 계정 또는 승인된 멤버 계정으로 로그인해 접속하기를 원한다. 접속 기기 등록·기기별 승인 절차는 요구하지 않는다.

중앙 서비스가 경로와 계정 인증을 제공하되, 파일·터미널·에이전트·화면 데이터는 사용자 서버와 브라우저 사이에서 직접 전송하는 방향을 선택한다. 도메인은 사용자가 보유한 saens.kr의 mew.saens.kr로 정한다.

## 선택지

1. 개인별 VPN·HTTPS 터널 설정을 기본으로 유지한다 — 현재 구현을 그대로 쓰지만 설치·접속 설정 부담을 해결하지 못한다.
2. 중앙 역방향 터널이 작업 데이터를 전달한다 — 브라우저 접속이 쉽지만 중앙 대역폭 비용과 데이터 처리 범위가 커진다.
3. 중앙 계정 인증·시그널링과 WebRTC 직접 전송을 분리한다 — 원하는 로그인 경험과 데이터 경로를 제공하지만 전송 계층 구현이 필요하고 일부 네트워크에서는 연결이 실패한다.

## 결정

3번의 설계 방향을 채택한다. 이 기록은 현재 서비스를 출시하거나 기존 인증을 변경했다는 뜻이 아니다.

- 중앙 접속 주소는 `https://mew.saens.kr/<user-id>/<device-name>`이다. device-name은 등록한 서버의 이름이며 접속 브라우저의 등록 이름이 아니다.
- 서버 A에서 로컬 owner가 최초 등록을 승인한다. 이후 A가 중앙 서비스와 인증된 연결을 자동 유지한다. B·C·D는 URL을 열고 계정으로 로그인하며 별도 VPN·접속 기기 등록·매번 A의 승인을 요구하지 않는다.
- 중앙 서비스는 신뢰된 웹 클라이언트 배포, 외부 계정 로그인, 서버 등록·경로, 접근 승인, 시그널링을 소유한다. 작업 데이터의 프록시·저장·실행은 하지 않는다. 인증·연결 메타데이터는 작업 데이터와 구분한다.
- 파일·터미널·에이전트·협업 전송에는 WebRTC DataChannel을 사용한다. A가 계정 신원과 접속 증명을 검증하고 로컬 역할·기능·파일 권한으로 최종 인가한다. 중앙 로그인이나 URL만으로 owner·셸 권한을 부여하지 않는다.
- 외부 계정의 안정적인 식별자와 로컬 mew 계정의 연계는 명시적으로 승인한다. 이메일 문자열만으로 기존 계정을 자동 연결하지 않는다. 기존 Git 제공자 연결과 AI 공급자 인증은 별개의 계약으로 유지한다.
- 서버는 네이티브 설치와 loopback HTTP 바인딩을 유지한다. 공개할 HTTP 포트·개발 서버·임의 로컬 서비스 프록시를 추가하지 않는다. `/user-id/device-name`은 중앙 웹 클라이언트의 선택 경로이며 로컬 mew를 하위 경로에 배포하는 것이 아니다.
- 초기 경로는 직접 연결만 사용한다. STUN은 주소 발견에 사용하며 TURN·중앙 작업 데이터 중계는 자동 추가하지 않는다. 직접 연결 실패를 명시하고 연결 가능한 환경만 지원한다. TURN 도입은 데이터 경로·비용·보안 계약을 함께 검토한 별도 후속 결정이 필요하다.
- 기존 원격 데스크톱의 직접 전송·OS 승인·단일 제어 연결·입력 lease는 [0189](0189-mew-desktop-external-direct-connectivity.md)와 현행 계약을 유지한다. 앱 원격 접속 추가로 영상 중계를 허용하지 않는다.
- 중앙 인증·접속 증명 서명·웹 코드 배포·운영 관리자 권한을 보호하고 분리한다. 중앙 발급 권한과 배포 코드에 대한 신뢰는 남으며, P2P 암호화가 중앙 서비스 완전 침해에 대한 안전을 보장한다고 표현하지 않는다.

## 근거

계정 로그인은 접속 기기 등록 없이 사용할 수 있다. 시그널링과 실제 전송의 분리는 사용자 서버에서 실행·저장을 유지하면서 중앙의 작업 데이터 전송 비용과 보관 범위를 줄인다. 대신 WebRTC는 일반 HTTP 서비스의 주소를 자동으로 공개하지 않으므로 앱 요청·실시간 이벤트를 전달하는 계층이 필요하다. 직접 연결 성공률은 실제 네트워크에서 검증해야 한다.

기술 근거는 [WebRTC 연결 설명](https://webrtc.org/getting-started/peer-connections), [DataChannel RFC 8831](https://www.rfc-editor.org/rfc/rfc8831.html), [WebRTC 보안 RFC 8827](https://www.rfc-editor.org/rfc/rfc8827.html), [OAuth 보안 RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)이다.

사용 흐름·신원 연계·전송·운영 보안·실패 처리·출시 검증의 기준본은 [계정 기반 P2P 원격 접속 설계](../../work/remote-access.md)다. 구현 전 현재 인증·배포·원격 데스크톱 동작의 기준본은 기존 프로젝트 문서를 따른다.
