## 배경

한 사용자의 프로젝트 탭 전환이 서버 전역 루트를 변경하고 모든 접속자의 화면도 전환했다. 알림만 제한하면 다른 계정의 파일 요청이 바뀐 루트를 향하므로 저장 소유권과 경로 해석을 함께 분리해야 한다.

## 선택지

1. 전환 알림만 계정에 제한한다 — 화면은 남지만 파일 요청의 루트가 바뀐다.
2. 활성 루트와 요청 경로를 계정별로 분리한다 — 기존 API 식별자를 유지하면서 비동기 작업·캐시·협업 경계를 보완한다.

## 결정

- 2번을 채택한다. 계정 UI 원장에 마지막 활성 루트 절대경로를 저장한다. 초기값이 없거나 폴더가 사라졌으면 서버 시작 루트를 사용한다.
- HTTP와 프로젝트 경로를 사용하는 WebSocket 연결은 인증된 계정에서 루트를 결정하고 요청/연결 컨텍스트에 고정한다. 비동기 처리 중 다른 계정의 전환이 경로를 바꾸지 않는다.
- 루트 전환은 기존 owner 권한을 유지하며 같은 계정의 접속에만 `workspace` 알림을 보낸다. guest와 다른 계정의 활성 루트는 유지한다.
- 계정 전환은 서버 시작 루트·환경 설정을 바꾸거나 공용 watcher·협업 방을 종료하지 않는다. 파일 목록·검색 상태·watcher와 협업 방은 실제 프로젝트 경로로 분리한다. 같은 프로젝트의 공동 편집은 계속 공유한다.
- SPA 전환·루트별 브라우저 캐시와 기존 에이전트의 고정 작업 경로는 유지한다. 기존 열린 탭 목록·그룹의 기기 간 실시간 동기화는 추가하지 않는다.
- 계정 없는 CLI·서버 초기화의 기본 루트는 기존 설정을 사용한다.

## 근거

인증된 계정의 루트를 비동기 컨텍스트에서 해석하면 모든 파일 API에 새로운 경로 인자를 추가하지 않고 동시 요청을 분리할 수 있다. 실제 프로젝트 경로를 공유 상태의 키로 쓰면 서로 다른 루트의 동명 파일을 구분하면서 같은 파일의 공동 편집을 유지한다.
