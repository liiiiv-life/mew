## 배경

mew의 협업은 여태 같은 문서를 동시에 고치는 것(Yjs 방·presence 점)까지였다. 문서 밖에서
말을 주고받을 자리가 없어서, 같이 쓰는 사람에게 "이 문단 이상하다"를 전하려면 mew를 나가야 했다.
문서 안의 특정 구절을 가리켜 말할 방법도 없었다.

두 기능을 붙일 때 결정할 것이 셋이었다:

1. 채팅을 무엇으로 나를 것인가 — 새 WebSocket 경로인가, 있는 것을 태울 것인가
2. 코멘트를 어디에 저장할 것인가 — 본문 파일 안인가 밖인가
3. 코멘트가 어디에 붙는지를 무엇으로 적을 것인가 — 좌표인가, 글자인가

## 결정

### 1. 채팅은 presence 소켓(`/api/presence`)을 그대로 탄다

새 WS 경로를 만들지 않는다. presence 소켓은 이미 모든 화면에 하나씩 붙어 있고, 업그레이드
시점에 인증을 해석해 게스트를 구분하고 있다. 여기에 메시지 종류를 넷 더한다:

| 방향 | 메시지 |
| --- | --- |
| 클라이언트 → 서버 | `{type:'chat', text}` |
| 서버 → 클라이언트 | `{type:'chat_history', messages}`(붙을 때 한 번) · `{type:'chat', message}` · `{type:'comments', project, path}` |

- 보낸 사람은 소켓의 신원이다. 본문에 실려 온 이름은 쓰지 않는다
- 방은 워크스페이스에 하나다. 채널·DM 목록은 없다 — 프로젝트를 옮겨도 같은 대화가 뜬다
  (에이전트 창과 같은 스코프)
- 최근 500줄만 `.data/chat.json`에 남는다. 원장이 아니라 최근 기록이다
- 경계는 로그인한 멤버 전체다(터미널·에이전트의 owner/manager보다 넓다). 게스트는 보내지도
  받지도 못하고 기록도 내려받지 못한다

### 2. 코멘트는 본문 파일에 한 글자도 쓰지 않는다

값은 그 프로젝트의 `<프로젝트>/.mew/comments.json`에만 산다(`.mew/table-layout.json`과 같은 자리).

- 코멘트를 달았다고 `.md`가 지저분해지거나 git diff가 생기면 안 된다 — 문서와 대화는 수명이 다르다
- 노란 칠은 데코레이션이다(ProseMirror `Decoration` / CodeMirror `Decoration`). 문서에 마크를
  넣지 않으므로 복사하면 글자만 가고 저장 결과에도 흔적이 없다 — 각주(ADR 없음, README 참고)와 같은 원칙
- 문서를 옮기거나 이름을 바꾸면 코멘트도 같은 요청에서 함께 옮긴다. 안 옮기면 통째로 미아가 된다

### 3. 붙는 자리는 좌표가 아니라 인용문 + 앞뒤 문맥이다

`{ quote, prefix, suffix }` 하나로 적고, 열 때마다 지금 본문에서 다시 찾는다
(`@mew/ui`의 `commentAnchor.ts` — W3C Web Annotation의 TextQuoteSelector와 같은 방식).

- 좌표는 못 쓴다. 앞을 한 글자만 고쳐도 전부 밀린다
- Yjs 상대 좌표도 못 쓴다. 방이 살아 있는 동안만 유효한데, 코멘트는 파일이 닫혀 있어도 살아야 한다
- 이 표기라야 좌표계가 다른 두 화면(md 렌더 화면 Hotview·원문 화면 Plain)이 같은 값 하나를
  본다. 화면마다 훑는 텍스트만 다르고 찾는 함수는 하나다
- 찾는 순서는 엄격한 것부터: `prefix+quote+suffix` → 문맥을 반씩 줄여 가며 → `quote` 단독
- 못 찾으면 그리지 않는다. 그 코멘트는 목록 팝업에만 남고, 눌러도 자리를 못 찾으면 그 사실을
  안내한다. 엉뚱한 자리에 노란 칠을 하는 것보다 안 그리는 쪽이 낫다
- 선택 없이 커서 자리에 남긴 코멘트는 `quote`가 빈 문자열이고, 화면에는 작은 네모로 선다

### 4. 멘션은 `@`지만 채팅과 코멘트가 서로 다른 것을 가리킨다

- 채팅의 `@` = 파일. 보낸 글에는 `[제목](<프로젝트 상대 경로>)` 형태로 남고 화면에는 제목만 뜬다.
  누르면 같은 창의 에디터 탭에서 열린다(새 창·새 주소 아님). Ctrl+L도 같은 토큰을 넣는다
- 코멘트의 `@` = 사람. 본문에는 `@이메일`이라는 글자만 남고, 배달은 서버가 한다
- 멘션된 사람에게는 채팅 한 줄이 간다. 그 줄은 `to: [이메일…]`이 붙어 보낸 사람과 지목된
  사람에게만 배달·복원된다. "해당 유저의 채팅창으로 보낸다"가 이 필드 하나로 성립한다

## 근거

- 소켓을 하나 더 만들지 않은 이유: 경로가 하나 늘면 인증 경계(`authorize*`)와 재접속·정리
  경로가 한 벌 더 생긴다. presence는 채팅과 수명이 정확히 같다 — 화면이 떠 있는 동안 붙어 있다
- `.data/chat.json`인 이유: 목록이 프로젝트별이 아니라 전역 하나라서다(`.data/term-button.json`과
  같은 근거). 프로젝트 폴더에 두면 프로젝트를 옮길 때마다 대화가 갈라진다
- 코멘트만 프로젝트 폴더인 이유: 코멘트는 그 문서의 것이라 문서와 함께 옮겨지고 백업돼야 한다
- 코멘트 열람 경계를 파일 열람 승인이 아니라 로그인으로 잡았다. 게스트에게 파일을 보여 주는
  것과 팀 내부 논의를 보여 주는 것은 다른 결정이다

## 결과

- 채팅 기록은 500줄이 넘으면 앞에서부터 사라진다. 남길 것은 문서에 쓴다 — 채팅은 기록 매체가 아니다
- 한 방뿐이라 사람이 늘면 시끄러워진다. 채널·DM이 필요해지면 `to`가 이미 있으므로 수신자 있는
  메시지를 목록으로 묶는 방향으로 늘린다(새 저장 형식이 필요 없다)
- Hotview에서 단 코멘트를 Plain에서 열면 자리를 못 찾을 수 있다 — 마크다운 표기(`굵게`)가
  인용문과 어긋나기 때문. 이 경우 목록에는 남고 본문에는 안 그려진다. 화면을 되돌리면 다시 보인다
- 본문에서 인용문이 완전히 지워지면 그 코멘트는 영영 자리를 못 찾는다. 지우는 것은 사용자 몫이다
  (자동으로 지우지 않는다 — 남의 글이다)
- 코멘트 변경은 presence의 `{type:'comments'}` 신호로 알리고 받은 쪽이 다시 받아 간다.
  내용을 방송하지 않는 이유는 게스트가 붙어 있는 소켓이기 때문이다
