## 배경

기존 `/api/file`은 파일 전체를 동기로 읽어 전체 문자열을 브라우저에 보내고, CodeMirror도 전체 문서를 만든 뒤에야 검색 결과의 목표 줄로 이동했다. 큰 plain 파일에서 사용자가 실제로 원하는 것은 목표 줄을 먼저 보는 것이므로, 전체 전송·문서 생성이 첫 표시를 불필요하게 막는다.

## 결정

검색 결과처럼 목표 줄이 있는 큰 plain 파일은 `/api/file`의 range 요청으로 목표 줄 주변 한 조각을 먼저 받는다. 서버 응답은 반환 줄 범위·파일 버전(size + mtime)을 포함한다. 첫 조각은 목표 줄보다 약 10% 앞에서 시작하며, 클라이언트는 이를 읽기 전용 plain preview로 즉시 표시한다. 전체 줄 수는 첫 응답을 위해 파일 끝까지 스캔하지 않고, 뒤의 전체 본문 전환 뒤에 확정한다. 전체 본문 요청은 그 뒤 비동기로 시작하고, 완료되면 기존 편집·협업·댓글 경로로 원자적으로 전환한다.

- 첫 적용은 프로젝트 내부의 plain 파일과 검색 결과 이동뿐이다. Markdown Hotview·외부 파일·미디어·협업 문서는 기존 전체 본문 경로를 유지한다.
- 부분 preview는 저장·입력·댓글 앵커·협업을 시작하지 않는다. 아직 받지 않은 본문을 저장해 지우는 경로를 만들지 않는다.
- 큰 파일 기준은 서버가 512 KiB 이상일 때다. 그보다 작은 파일의 range 요청은 호환되는 전체 본문 응답으로 끝낸다.
- 전체 본문을 받은 뒤 cache에 넣는다. 조각만 cache에 넣어 다음 열기에서 불완전한 문서를 복원하지 않는다.

## 근거

이 경계는 CodeMirror의 DOM viewport 최적화보다 앞선 전송과 전체 문서 생성 비용을 피한다. 부분 상태를 편집 가능한 문서나 Yjs 방으로 취급하지 않으므로 [ADR 0035](0035-mew-collab-rooms-rust-yrs.md)의 방 수명·동기화 불변식도 바꾸지 않는다. 파일 버전은 뒤늦은 전체 응답 또는 파일 변경을 식별할 최소 계약이다.

## 결과

- 큰 파일을 일반 클릭으로 열 때와 목표 줄이 없는 경우에는 전체 본문 경로가 유지된다.
- 첫 range 구현은 서버에서 비동기 읽기를 사용한다. 줄 오프셋 인덱스·인접 청크 `0,+1,-1` 보충·placeholder scrollbar는 계측에서 첫 preview가 충분히 빨라졌다는 확인 뒤 별도 확장으로 결정한다.
- preview와 전체 응답의 version이 다르면 preview를 유지한 채 최신 전체 응답만 적용한다. 부분 조각을 이어 붙여 저장하지 않는다.
